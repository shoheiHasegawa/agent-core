# SKILL: TDD Green Refactorer (Implementer)

このファイルは、特定のタスクを実行するための具体的な手法（Layer 3）を定義する。

## 🎯 目的 (ミクロな WHY)
なぜこのスキル（手順）が存在するのか。
- 用意された防波堤（テスト）の上で、最短でテストをパス（Green）させ、その直後にクリーンアーキテクチャへとリファクタリングするサイクルを回すため。
- テストが通らないからといってテストコード側を書き換える不正を防ぎ、テストの信頼性（防波堤）を担保するため。

## 📥 入力と出力 (ミクロな WHAT)
※ ここでのWHATはシステム大局の目的ではなく、このスキル（関数）が受け取るべき「前提条件・インターフェースの制約」である。
- **Input**: `tdd-red-builder` が作成した失敗する結合テスト（Outer Red）と対象の仕様書 (`spec.md`)
- **Output**: クリーンでテスト済みのプロダクションコード (`src/` 配下)

## 🛠️ 実行手順 (HOW)
具体的にどうやってタスクを達成するか。
1. 結合テストをパスさせるための最小限の実装（`src/` 配下）を行う。複雑なビジネスルールがある場合は `tests/unit/` 配下に単体テストを作成しながら実装を肉付けする。すべてのテスト（Integration + Unit）が PASS（Green）するまで実装を進める。
2. 全パス状態（Green）になったら、対象リポジトリの実装ルール（`core-service/docs/rules/ddd_guidelines.md` など）を直接JITロードし、リファクタリングを行う。リファクタリング中も常にテストを回し続け、Green状態を維持する。
3. `make check-all` を実行し、Linterエラーゼロおよびテスト網羅を確認する。
4. [完了条件 / Exit Criteria] 全ての品質ゲート（Linter、テスト）をパスした後、標準の報告フォーマット（Reporting Contract）にて親エージェントへ報告し終了する（独自の出力契約は使用しない）。
