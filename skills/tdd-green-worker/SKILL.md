# SKILL: TDD Green Worker (Implementer)

このファイルは、特定のタスクを実行するための具体的な手法（Layer 3）を定義する。

## 🎯 目的 (ミクロな WHY)
- テストコードを勝手に書き換える不正を防ぐため、テストを「絶対の防波堤」として扱い、それをパスさせる実装のみに集中するため。
- **（重要）** 隔離されつつも、仕様書（WHY/WHAT）のドメイン知識を読み取ることで、表面的なテストパスではなく、DDD原則等に基づいた本質的なドメインモデリングとリファクタリングを実現するため。

## 📥 入力と出力 (ミクロな WHAT)
- **Input**:
  - `spec.md` (仕様書: ドメインモデリングと意図の把握用)
  - `tdd-red-worker` が作成したテストコードのパスと実行結果
  - `docs/templates/Reporting_Contract_Template.md` (報告の型)
  - 設計ルール（親から指定されたDDDガイドラインなど）
- **Output**: クリーンでテスト済みのプロダクションコード（親へは Reporting Contract 形式で報告）

## 🛠️ 実行手順 (HOW)

このワーカーはテストコードの修正（不正）を行ってはならない。

**【厳格な制約: 先回り実装の禁止】**
`spec.md` はあくまでドメインモデリング（変数命名やクラス設計）の参考としてのみ参照すること。**テストコードで要求（アサート）されていないビジネスロジックを、仕様書を読んで先回りして実装することは固く禁ずる**。テストの漏れ（テストがスカスカな状態）を検知した場合は勝手に実装せず、`Reporting Contract` で親へエスカレーションせよ。

1. **JITロード**: 親（オーケストレーター）から指定された設計ルール、`spec.md`、およびテストコードの状況を把握する。
2. **Green実装**: テストをパスさせるための最小限の実装（プロダクションコード）を作成する。
3. **テスト検証**: 全てのテストが PASS（Green）になるまで実装と修正を繰り返す。
4. **リファクタリング**: Green状態を維持したまま、読み込んだ設計ルールに従ってコードをリファクタリングする。
5. **報告の型による完了**: `agent-core/docs/templates/Reporting_Contract_Template.md` を読み込み、そのフォーマットに厳密に従って親に結果を報告して終了する。
