# Skill: SDD Spec Writer (Loop 1: Co-Creation Discovery)

## 🎯 目的
ユーザーとの対話を通じて「何を作るか（What to Build）」の背景と意図を深掘りし、6大観点のストレステストにより仕様の穴（エッジケース・境界値）を実装前に炙り出し、ユーザーと合意された仕様書（`spec.md`）を共創する。

## ⚠️ 制約事項 (Constraints)
1. **即答バイアスの禁止（対話の強制）**: いきなり完成版の `spec.md` を出力してはならない。必ずユーザーへの背景ヒアリングおよびエッジケースの問いかけ（壁打ち）から開始すること。
2. **SSOTの厳守**: `spec.md` は `agent-core/templates/spec_template.md` のフォーマットに従い、時系列や議論経緯を含まない「最新の確定した真実（Timeless SSOT）」として記述すること。
3. **Human Gate の厳守**: ユーザーからの明示的な「Approve（承認）」を得るまで、後続の TDD 実装（Loop 2）へ進んではならない。

## 🛠️ 実行手順

### 1. ルールのJITロードと要求の具体化 (Socratic Discovery)
*   **入力 (Input)**: ユーザーからの要求・課題・バグ報告
*   **アクション (Action)**: `agent-core/docs/rules/sdd_tdd_heuristics.md` をJITロードし、それを踏み台として「なぜこの機能が必要なのか、最も解決したいユースケースは何か」を深掘りする。
*   **メタ認知と揺らぎ (Whyの注入)**: 
    - 単に御用聞きになるのではなく、意図的な揺らぎとして「あえて極端な仮説（What if）」や「既存の仕組みで代用できないか（YAGNI）」をぶつけてユーザーの思考を揺さぶること。
    - ユーザーの認知負荷を下げるため、最も本質的な1〜2問に絞り込んで対話すること。

### 2. 反証可能なエッジケース探索 (Edge-Case Probing)
*   **アクション (Action)**: 仕様の穴を突く反証可能な質問をユーザーに提示する。
*   **Edge Case Few-Shot (Good/Bad対比)**:
    - **競合・並行性**:
        - [Bad] 「同時にアクセスされたらどうしますか？」
        - [Good] 「ユーザーAが編集中にユーザーBが削除した場合、Aの保存時にどうエラーを返しますか？」
    - **異常系・破損耐性**:
        - [Bad] 「エラーが出たらどうしますか？」
        - [Good] 「外部APIが503を返したままリトライ上限に達した場合、データは『保留』ステータスで永続化しますか？」
    - **ドメイン不変条件**:
        - [Bad] 「データがおかしい時は？」
        - [Good] 「『残高がマイナスにならない』という制約は、どの操作のタイミングで検証（バリデーション）しますか？」

### 3. 仕様書のドラフト生成とスタブ配置
*   **アクション (Action)**:
    - 対話で合意された内容を `src/application/<機能名>/spec.md` に反映する。
    - `src/application/<機能名>/` 配下に空のスタブ（DTOやUseCaseクラス）を配置する。
*   **制約事項 (Constraints)**: 入出力データ型、エッジケース時のドメインエラー型、6大観点シナリオID（例: `[TM-PLAN-01]`）を明確に定義すること。

### 4. ユーザー承認の獲得 (Human Gate)
*   **アクション (Action)**: 作成した `spec.md` の要点を提示し、「仕様の穴はすべて塞がりました。この内容で TDD 実装（Loop 2）へ進んでよろしいでしょうか？」とユーザーに承認（Approve）を求める。
*   **出力 (Output)**: ユーザー承認済みの `spec.md` およびインポート可能なスタブ群。承認が得られたら `sdd-loop-orchestrator` へバトンタッチする。
