# Skill: SDD Spec Writer (Loop 1: Co-Creation Discovery)

## 🎯 目的
ユーザーとの対話を通じて「何を作るか（What to Build）」の背景と意図を深掘りし、6大観点のストレステストにより仕様の穴（エッジケース・境界値）を実装前に炙り出し、ユーザーと合意された仕様書（`spec.md`）を共創する。

## ⚠️ 制約事項 (Constraints)
1. **即答バイアスの禁止（対話の強制）**: いきなり完成版の `spec.md` を出力してはならない。必ずユーザーへの背景ヒアリングおよび6大観点の問いかけ（壁打ち）から開始すること。
2. **ロジック実装の禁止**: ビジネスロジックの実装（具体的なアルゴリズムや計算）は行ってはならない。ただし、後続のTDDワーカー（`tdd-red-coder`）がインポートエラーで立ち往生するのを防ぐため、空の型シグネチャ・インターフェース（`raise NotImplementedError("TODO: Implement in Inner TDD")` を含むスタブ）の配置のみ許可される。
3. **SSOTとテンプレートの厳守**: `spec.md` は `agent-core/templates/spec_template.md` のフォーマットに従い、時系列や議論経緯を含まない「最新の確定した真実（Timeless SSOT）」として記述すること。
4. **Human Gate の厳守**: ユーザーからの明示的な「Approve（承認）」を得るまで、後続の TDD 実装（Loop 2）へ進んではならない。

## 🛠️ 実行手順

### 1. 要求のヒアリングと具体化 (Socratic Discovery)
*   **入力 (Input)**: ユーザーからの要求・課題・バグ報告
*   **アクション (Action)**: なぜこの機能/改修が必要なのか、最も解決したいユースケースは何かを対話によって深掘りする。
*   **制約事項 (Constraints)**: 1ターンに投げかける質問は最大3問までに絞り、ユーザーの思考負荷を抑えること。

### 2. 6大観点ストレステスト (Edge-Case Probing)
*   **アクション (Action)**: 対象リポジトリの `docs/rules/testing_strategy.md` に定義された6大観点に基づき、潜在的な仕様の穴を突く質問をユーザーに提示して仕様を決定する:
    - **① 冪等性**: 「同一操作が連続実行された場合や、日中に再実行された場合の挙動は？」
    - **② 境界値**: 「データが0件の時や、日付境界（00:00跨ぎ）の時の挙動は？」
    - **③ 外部調停**: 「外部システム側で手動変更・競合があった場合の優先ルールは？」
    - **④ 破損耐性**: 「一部のデータが不正・破損していた場合のフォールバックは？」
    - **⑤ ドメイン不変条件**: 「システムが絶対に破ってはならない制約は何か？」

### 3. 仕様書のドラフト生成とスタブ配置
*   **アクション (Action)**:
    - 対話で合意された内容を `src/application/<機能名>/spec.md` に反映する。
    - `src/application/<機能名>/` 配下に空のスタブ（DTOやUseCaseクラス）を配置する。
*   **制約事項 (Constraints)**: 入出力データ型、エッジケース時のドメインエラー型、6大観点シナリオID（例: `[TM-PLAN-01]`）を明確に定義すること。

### 4. ユーザー承認の獲得 (Human Gate)
*   **アクション (Action)**: 作成した `spec.md` の要点を提示し、「仕様の穴はすべて塞がりました。この内容で TDD 実装（Loop 2）へ進んでよろしいでしょうか？」とユーザーに承認（Approve）を求める。
*   **出力 (Output)**: ユーザー承認済みの `spec.md` およびインポート可能なスタブ群。承認が得られたら `sdd-loop-orchestrator` へバトンタッチする。
