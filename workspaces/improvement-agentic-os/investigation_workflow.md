# Agentic OS ワークフローアーキテクチャ調査結果：Hard Constraint化に向けた技術的負債と欠陥

現在の `you_inc/agent-core/` ディレクトリ群（`tools/`, `docs/rules/`, `AGENT.md` など）を調査した結果、Agentの行動ルールや制約が「プロンプトエンジニアリング（Soft Constraints）」に過度に依存しており、システム的に強制（Hard Constraints）するためのアーキテクチャに深刻な欠陥・技術的負債が存在することが判明しました。

## 1. 根本的なアーキテクチャ上の欠陥

### (1) ミドルウェア・インターセプター層の不在
現状、Agentは `default_api:run_command` などのツールを通じて直接シェルやファイルシステムを操作しています。ツール（`tools/` 配下のPythonスクリプト）は独立したCLIとして実装されているため、**AgentOS側でLLMの思考ループ（Thought -> Action）の間に介在し、実行前後にロジックを挟み込む（Middleware Interception）仕組みが存在しません。**
これにより、実行前のパラメータ検証や、実行後のフック（自動テスト実行、自動記録など）をシステム的に強制できません。

### (2) プロンプト（Soft Constraints）への過度な依存と自己採点制
`AGENT.md` や `docs/rules/*.md` において、「Handoff前に `make check-all` を実行すること」や「Zero-Shotを禁じる」といったルールが明記されていますが、これらは全て**LLMの自律的な遵守（プロンプト指示）**に依存しています。
Agentが指示を無視してタスクを完了（終了コードを返却）してしまうことを物理的にブロック（Gatekeeper）する機構がなく、確実性が担保されていません。

### (3) Context Pre-loadingの欠如（AgentへのJITロードの丸投げ）
`<jit_routing>` や `_index.md` によるコンテキストルーティングは、Agent自身が「気づいて手動で `view_file` や `cat` で読み込む」ことに依存しています。特定のディレクトリやタスクに入った際に、必要なコンテキストをシステム側が事前（あるいはツール呼び出し時）に自動で注入・ロードする仕組み（Context Pre-loading）がないため、Agentのコンテキスト漏れ（記憶喪失）が発生しやすい構造です。

### (4) ツール呼び出しの不透明性（CLIとしての実行）
Agentは提供されたツール（例: `tools/update_task.py`）を「シェルコマンドの一部」として実行しています。もしこれらがAgent OSネイティブな関数（Function Calling）やMCP（Model Context Protocol）ツールとして登録されていれば、OS側でペイロードを横取りし、権限チェックやフォーマット検証をHard Constraintとして強制できますが、現状のCLI呼び出しではOSにとって「ただの文字列の実行」に過ぎません。

## 2. MUSTレベルの技術的負債（早急な対応が必要な課題）

1. **Gatekeeperの不在**
   - **問題**: 破壊的変更やルール違反（例: 未テストコードのコミット、指定外ディレクトリへの書き込み）をOSレベルでブロックできない。
   - **解決策の方向性**: シェル実行ツール (`run_command`) やファイル操作ツールの入出力をインターセプトし、禁止パターンや必須条件（品質ゲートの通過状態）を満たしていない場合はエラーを返すGatekeeper層（プロキシツール）の導入。

2. **静的ルールファイルの手動ロード**
   - **問題**: `AGENT.md` などのローカルルールをLLMが読み忘れると、全ての規律が崩壊する。
   - **解決策の方向性**: Agentのコンテキストウィンドウ構築時に、カレントディレクトリやタスクの種類に応じて必須ドキュメント（`SKILL.md` や `AGENT.md`）を自動的にシステムプロンプトに結合（Pre-load）する動的コンテキスト管理層の構築。

3. **ツールの「JSON-First」のプロンプト依存**
   - **問題**: `tool_design_principles.md` でJSON入出力を定めているが、LLMが誤った引数やフォーマットでCLIを叩くことを防げない。
   - **解決策の方向性**: スクリプトベースのツール群を、LLMの関数呼び出し（Native Tool/MCP）スキーマに昇華し、型定義とバリデーションをAPIレベルで強制する。

## 結論
現状の Agentic OS は「ルールを詳細に書き、LLMに賢く守ってもらう（Soft Constraints）」という性善説の設計になっています。これをHard Constraintsに移行させるためには、**Agent（LLM）と実行環境（Shell/File System）の間に、Tool Proxy・Interceptorとなるミドルウェア層を挟み込み、ルールの検証とコンテキストの自動注入をシステム側が担うアーキテクチャ**への抜本的なリファクタリングが不可欠です。
