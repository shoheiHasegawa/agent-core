# Skill Complexity Analysis: MUST-level Risks & Cognitive Overload

`you_inc/agent-core/skills/` 配下の主要なスキルファイル（`sdd-spec-builder`, `tdd-red-builder`, `sdd-loop-orchestrator`, `global-alignment-reviewer`, `compliance-reviewer`, `skill-architect` など）を精査した結果、プロンプトの肥大化やAgentに対する過度な認知負荷、およびシステムを破綻させる「不可能論理ループ」のMUSTレベルのリスクが複数発見されました。

以下に詳細な深掘り調査結果を報告します。

## 1. 無限ループリスク（不可能論理ループ / MUSTレベル）

自律ループを制御するスキルにおいて、リトライ上限が設定されていない、または解決不可能な差し戻し指示が存在し、Agentがトークンを無限に消費するリスクがあります。

- **`sdd-loop-orchestrator/SKILL.md`**
  - **上限のない再試行**: Phase 3 (Quality Gate) には `[Retry Count: N/3]` という明確な上限がありますが、Phase 2 (Inner Loop) の「失敗時はエラーログを添えて tdd-green-refactorer に再委譲する」および Phase 4 (Compliance Review) の「Rejectされた場合は... Phase 2 へ差し戻す」には**リトライ上限の記述が一切ありません**。テストが通らない、あるいはレビューアの指摘が抽象的で修正できない場合、Agentはここで無限ループに陥ります。
  - **解決不能な差し戻し先**: Phase 1 (Outer Red) にて、「スタブ起因の致命的エラーの場合は、スタブ作成元へ差し戻して型シグネチャを修正させる」とありますが、このスキル内で呼び出しているのは `tdd-red-builder` のみです。スタブを作成したのは先行フェーズの `sdd-spec-builder` であり、現在のコンテキストを持たないオーケストレーターが「誰がスタブ作成元か」を特定し差し戻すフローは定義されておらず、エラー時にAgentがフリーズ・混乱する原因となります。

- **`skill-architect/SKILL.md`**
  - **上限のない再審査**: 「`skill-reviewer` からの指摘があれば即座にリファクタリングして再審査を受ける。Passを獲得し、かつ `audit_skills.py` がエラー0件で通過するまで完了しない」と定義されています。これも上限回数がなく、レビュアーとアーキテクトの間で意見が割れたり、Linterの仕様に合わない修正を繰り返した場合に無限ループを引き起こします。

## 2. 過度な認知負荷と矛盾した指示（Cognitive Overload & Paradox）

メタ認知や高度な推論を要求するレビュースキルにおいて、LLMのコンテキストウィンドウを圧迫し、ハルシネーションを誘発する重い処理が存在します。

- **`global-alignment-reviewer/SKILL.md`**
  - **過度な動的DI（Dynamic Dependency Injection）**: 「動的DIの例外特権」として、憲法(`GEMINI.md`)、アーキテクチャ原則、各所の `_index.md` を読み込み、さらにそこから必要なドキュメントを特定してJITロードするよう指示されています。
  - **リスク**: 多階層にわたるドキュメントの探索・抽出・統合を1ターンのプロンプト内で要求しており、Agentの認知負荷が極めて高くなっています。関連性の薄い大量のコンテキストを引き込んでしまい、肝心の「局所最適化の監査」というタスクの精度が低下する（または文脈崩壊を起こす）可能性が高いです。

- **`compliance-reviewer/SKILL.md`**
  - **矛盾した指示（Paradox）**: 「関連するルールのみを特定して一時的な『チェックリスト』を構築する。無差別な全読みは避ける」という指示がありますが、LLMの性質上、テキストの中身を解釈せずに「関連するかどうか」を判定することは不可能です。事実上、ツールを使って大量のファイルを読んだ上で取捨選択する重い処理を強いることになります。
  - **主観的評価への依存**: 「ルールの字面だけでなく、その真の意図（Why）に反していないかを深く推論・評価する」という指示は、プロンプトを肥大化させるだけでなく、レビュー基準を非常にブレやすく（非決定的に）しています。これが前述の `sdd-loop-orchestrator` での無限差し戻しループを誘発する一因となります。

## 3. 暗黙の依存と未定義動作（Implicit Dependencies）

- **`sdd-spec-builder/SKILL.md`**
  - **出力仕様の曖昧さ**: Outputとして「インポート可能なスタブ群（DTOやUseCaseクラス等）」を要求していますが、具体的なディレクトリ構成、クラスの命名規則、型ヒントの厳密さなどのガイドラインが一切示されていません。
  - **下流への悪影響**: ここで生成されたスタブが不完全な場合、直後の `sdd-loop-orchestrator` Phase 1 で致命的エラー（`AttributeError` / `TypeError`）となり、前述の「解決不能な差し戻し」の罠に直行することになります。

## 総括と改善案

現在のスキルセットは、各Agentに高度な自律性を持たせようとするあまり、**「終了条件のないループ」「無限の探索」「主観的で重い評価」**が複雑に絡み合っており、運用時に容易に破綻するMUSTレベルのリスクを抱えています。

**推奨される具体的な改善アクション：**
1. **フェイルセーフの導入**: すべてのループ処理（`sdd-loop-orchestrator` のPhase 2/4、`skill-architect` の再審査）に、明示的な最大試行回数（例: `MAX_RETRIES: 3`）を設け、超過時は人間にエスカレーションして停止するルールを追記する。
2. **依存関係・差し戻しパスの明確化**: `sdd-loop-orchestrator` Phase 1 でスタブエラーが起きた際、「誰に・どうやって」差し戻すのか（例: ユーザーに通知して停止する、特定のサブエージェントを再起動するなど）を具体的に定義する。
3. **動的DIの制限と静的コンテキストへの移行**: `global-alignment-reviewer` などの探索範囲に上限（例: 「読み込む `_index.md` は最大2つまで」）を設けるか、複雑なルール抽出ロジックはPythonスクリプト（ツール側）に隠蔽し、LLMの認知負荷を下げる。
