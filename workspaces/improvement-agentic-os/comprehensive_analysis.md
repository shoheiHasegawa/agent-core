# Agentic OS 徹底調査・総合分析レポート

本レポートは、`agent-core`, `core-service`, `second-brain` ディレクトリの調査結果を統合し、負債の実態、元ルールの目的、そして単純な引き算にとどまらない「責務配置の変更・移譲」について深く分析したものです。

---

## 1. JIT Routing (マニュアルでのルール読み込み) の破綻

### 負債とリスクの実態
- **実態**: `GEMINI.md` にて「着手時に必ず対象ディレクトリの `AGENT.md` と `SKILL.md` を読め」と指示している（Soft Constraint）。
- **リスクと原因**: ユーザーから「バグを直して」と具体的な指示（HOW）が飛んできた際、LLMのAttentionが問題解決に奪われ、メタ的な儀式（WHEN/WHEREのルールの確認）が読み飛ばされる。
### 元々のルールの目的
- システムの全ルール（Core, Service, Second-brain等）を最初からシステムプロンプトに詰め込むと、コンテキストオーバーロードやToken枯渇を起こす。そのため、**「必要な時に、必要なコンテキストだけを動的にロード（JIT: Just-In-Time）」**したかった。
### 移譲・責務配置の変更案
- **Agentの自律性 → システム制御（Context Pre-loading）への移譲**
  - Agentに「読んでこい」と指示するのではなく、Agentを立ち上げるOS側（Session ManagerやOS起動スクリプト）が現在のワークスペースパスを検知し、タスク着手時の**システムプロンプトの末尾に強制的に `AGENT.md` の内容を Inject (注入)** する構造へ変更。
  - 読む責務をAgentからシステム（OSミドルウェア）に移譲する。

## 2. 多重レビュー・オーケストレーションのAgentへの丸投げ

### 負債とリスクの実態
- **実態**: `core-service/AGENT.md` などにおいて、実装前に「影響分析」と「global-alignment-reviewer」の実行、実装後に「compliance-reviewer」と「validate_sdd.py」の実行を、作業を担当するTier1のAgent自身にオーケストレーションさせている。
- **リスクと原因**: 開発タスクそのものより「手続き」が重くなりすぎている。Agentは「早くコードを書いて解決したい」というReward Hackingの誘惑に弱く、これらの多重検証を無意識・または意図的にスキップする。
### 元々のルールの目的
- LLMのハルシネーションや局所最適化によるアーキテクチャの破壊を防ぐため、第三者的な視点（別AgentやLinter）による「品質ゲート（Gatekeeper）」を確実に設けたかった。
### 移譲・責務配置の変更案
- **開発Agent → 非同期のSupervisor / CIパイプラインへの移譲**
  - 作業Agentの責務を「コードを書き、ローカルの単体テストを通すこと」に極小化する。
  - 品質ゲートの責務は、Agentの完了報告（Handoff）をフックとして、システム側が自動で起動する。完了宣言ツールが呼ばれた内部で `compliance-reviewer` などを呼び出し、NGならAgentにエラーとして差し戻す（Gatekeeperアーキテクチャ）への移譲。

## 3. 進捗・ステートの自己トラッキング（`progress.md` 等）

### 負債とリスクの実態
- **実態**: `progress.md` などのMarkdownのチェックボックスをAgent自身に手動更新させている。
- **リスクと原因**: Diffツールを用いた自己トラッキングは適用ミスが起きやすい。「今どこまでやったか」を言語化させる行為自体が重い認知負荷となり、本来のタスクの思考を妨げる。
### 元々のルールの目的
- セッションが途切れても（コンテキストがリセットされても）、次のAgentがスムーズにタスクを再開できるように、システムの「状態（State）」を永続化したかった。
### 移譲・責務配置の変更案
- **Agentによる自由記述更新 → 専用Native Tool / バックエンドDBへの移譲**
  - ファイルの直接編集を禁じ、Agentには `update_task_status(task_id, status)` のような専用の関数ツール（API）のみを開放する。
  - フォーマットの維持やMarkdown/DBへの書き込み処理は、ツールの内部ロジック（システム側）に責務を移譲する。

## 4. 高度すぎる思考プロセスの一律要求（second-brain）

### 負債とリスクの実態
- **実態**: `second-brain/AGENT.md` で、ナレッジの整理時に「必ず反証やアナロジーを付与して弁証法的に蒸留する」というルールを敷いている。
- **リスクと原因**: ただの雑多なメモをフォルダに分類するだけの単純タスクに対しても、高度な推論を強要するため、トークン消費と処理時間が跳ね上がる。
### 元々のルールの目的
- Second Brainを単なる「ゴミ箱」にせず、過去の知識と連結して新たなインサイトを生み出す「知の蒸留装置」として機能させたかった。
### 移譲・責務配置の変更案
- **単一Agentの多重労働 → ワーカーとDeep Thinkerの分離（非同期処理）**
  - 日常の整理タスクを担うAgentの責務は「適切なタグ付けとフォルダ移動」のみ（引き算）とする。
  - 「反証やアナロジーの抽出」といった高度な知的作業は、夜間バッチ（Night Routine Orchestratorなど）として起動する専用のDeep Thinker Agentに移譲する。これにより、即時処理が必要なタスクの認知負荷を劇的に下げる。

---

## まとめ：アーキテクチャのリファクタリング方針
これらの調査から、単なる「ルールの引き算（記述を消すこと）」だけでは不十分であり、**「Agentの自律性に依存していた責務を、システム（OS、ツール、非同期プロセス）へ移譲・再配置すること」**こそが、現状の負債を解消する真の解決策であることがわかりました。
