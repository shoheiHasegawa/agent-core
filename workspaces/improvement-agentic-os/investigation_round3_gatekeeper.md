# 調査レポート (Round 3): Gatekeeper & Interceptor アーキテクチャ

## 1. 課題の背景 (Loop 2の発見から)
Loop 2における検証の結果、既存のツール群には以下の脆さ（Fragility）が存在することが判明しました。
- **エラー出力のトランケーション**: コマンド実行結果やビルドエラーなどの出力が単純に切り詰められる（Truncateされる）ことで、LLMが必要なコンテキストを失い、TDD（テスト駆動開発）における自己修復（Self-healing）ループが破壊される。
- **Enumや引数の検証不足**: LLMのハルシネーションによる不正な引数やEnum値の注入を防御しきれず、ツール側で想定外の挙動やクラッシュを引き起こす。

## 2. 解決策のアプローチ: 強固な傍受・検証レイヤーの導入
これらの問題を根本から解決するために、`agent-core/tools/` アーキテクチャ内に以下の3つのレイヤーを設計・実装します。

### 2.1 Interceptor (インターセプター) パターンによるI/O制御
- **目的**: ツール（例えば `run_command` や `view_file`）の標準出力/標準エラー出力を中継・加工し、LLMに最適な形でフィードバックを返す。
- **実装パス**:
  - `agent-core/tools/interceptors/` を新設。
  - **Error Output Summarizer**: エラー出力が一定長を超える場合、単なる末尾の切り捨てではなく、「最初のエラー原因（スタックトレースのトップ）」と「最後のエラーサマリ」を結合して返すなど、LLMが修復アクションを起こすために必要な情報を抽出するロジックを組み込む。
  - **Pagination/Offset Handler**: 長大な出力に対しては、強制的なトランケーションではなく、自動的に「続きを読む」ためのオフセット情報やPagination用の別コマンドを提案するメタデータを付与する。

### 2.2 Gatekeeper (ゲートキーパー) によるHard Constraintsの強制
- **目的**: ツール実行前の入力値に対する厳格なバリデーション（事前条件の強制）。
- **実装パス**:
  - `agent-core/tools/gatekeepers/` を新設。
  - PydanticやJSON Schema Validatorを利用した強力なリクエストバリデーションを導入。
  - **Enum Strict Matcher**: 定義されたEnum値以外の入力は即座にリジェクトし、LLMに対して「利用可能なEnum値の一覧」を含む明確でActionableなエラーメッセージを返す。
  - **Semantic Validator**: ファイルパスが正しいWorkspace内であるか（ディレクトリトラバーサルの防止）、破壊的なコマンドでないかを静的解析・正規表現で評価。

### 2.3 Native Tools (Function Calling/MCP) の再設計
- **目的**: LLMとのインターフェース（Function Calling）をより堅牢にし、自己修復を促進する。
- **実装パス**:
  - Model Context Protocol (MCP) を活用し、ツールのスキーマ定義（JSON Schema）と実際の実行ロジックを明確に分離。
  - ツールのパラメータに `description` を詳細に記述し、「この引数は必ず〜の形式でなければならない」というプロンプトレベルでの制約（Soft Constraints）を強化する。
  - ツール実行のタイムアウトやリトライロジックをNative Tool層で吸収し、LLM側には「タイムアウトしたため、クエリを絞って再実行してください」といった自己修復を促すエラーを返す。

## 3. `agent-core/tools/` におけるアーキテクチャ上の障害 (Roadblocks)
この設計を進める上で、現在の `agent-core/tools/` 実装において以下のブロッカーが想定されます。

1. **ツールのモノリシックな実装**:
   - 現状のツールが実行ロジックとI/O処理、バリデーションを密結合で持っている場合、InterceptorやGatekeeperを差し込むためのMiddleware機構（フックポイント）が存在しない可能性があります。
   - **解決策**: ツールインターフェースを抽象化し、リクエスト時とレスポンス時に介入できる `ToolMiddleware` や `ToolPipeline` といった概念を導入するリファクタリングが必要です。

2. **非同期実行（Background Tasks）との不整合**:
   - `run_command` のように非同期で実行され、後から結果が通知されるタスクに対して、Interceptorがどのタイミングで介入するか（メッセージ送信時か、タスク完了時か）のライフサイクル管理が複雑です。
   - **解決策**: イベント駆動型のメッセージング基盤とInterceptorを統合し、LLMへのメッセージ送信直前にコンテンツを評価・整形するパブリッシュ側の中間レイヤーを設ける必要があります。

3. **コンテキスト長と要約精度のトレードオフ**:
   - エラーをトランケートせずにLLMに渡す工夫（スマートサマリなど）は、要約アルゴリズム（正規表現や軽量なヒューリスティクス）の精度に依存します。誤って重要なトレースを要約してしまうリスクと、LLMのコンテキストウィンドウを溢れさせるリスクのバランスを取る必要があります。

## 4. 結論
GatekeeperとInterceptorをアーキテクチャの根幹に導入することで、LLMはツール実行の「失敗から確実に学ぶ（Self-healing）」ことが可能になります。直近のネクストアクションとして、`agent-core/tools/` にMiddlewareパターンを導入し、まずは `run_command` ツールのエラー出力制御と、EnumバリデーションのGatekeeperに対する概念実証（PoC）を開始することを推奨します。
