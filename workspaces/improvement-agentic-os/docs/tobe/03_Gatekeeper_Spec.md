# ゲートキーパーおよびツーリング層の仕様 (TO-BE)

## 1. 概要
この仕様書は、ゲートキーパーおよびツーリング層のTO-BEアーキテクチャを定義します。主な目標は、厳格なバリデーションによる堅牢な実行を保証し、エラー出力の隠蔽による解析不能状態を排除することです。
※ 以前検討されていた高度な自動復旧機構（Watchdogによる自律的プロンプト注入等）は排除し、ユーザーとフロントAgentの対話を通じた安全なリカバリ（Interactive Triggerモデル）を原則とします。

## 2. エラー出力切り詰めの排除
### 2.1 現状の問題点
現在、ツールやコマンドが失敗した際、結果のエラー出力（例: `stderr`、スタックトレース）は任意の長さ制限に収まるように切り詰められる（Truncate）ことがよくあります。これにより、Agentはエラーの根本原因を見ることができず、自律的な診断や自己修復が不可能になっています。

### 2.2 TO-BE アーキテクチャ
*   **完全なエラーの保持**: ゲートキーパーは、`stderr` や例外出力を強制的に切り詰めることをやめます。
*   **スマートなページネーション/ストリーミング**: 単一メッセージのコンテキストウィンドウの上限を超える出力の場合、ゲートキーパーは自動的に出力をページネーションするか、アクセス可能な一時アーティファクト（ファイル）に保存し、正確なファイルパスと要約をAgentに渡します。
*   **優先配信**: 致命的なエラーやスタックトレースは、必ず全文がAgentの即時コンテキストに届けられることを保証します。

## 3. 厳格な入力バリデーション (Native Tools)
### 3.1 現状の問題点
ツールの入力に対する緩いバリデーションは、予測不可能な下流での失敗、状態の破損、そしてAgentを混乱させて実行サイクルを無駄にする無益な実行時エラーを引き起こします。

### 3.2 TO-BE アーキテクチャ
*   **実行前のスキーマバリデーション**: ゲートキーパーは、すべてのツール入力に対して、それが基盤となる実行環境に到達する*前*に、JSONスキーマに裏付けられた厳格なバリデーションを強制します。
*   **実行可能なフィードバック**: バリデーションが失敗した場合、ゲートキーパーは不正なフィールド、期待される型、および制約を正確に示す構造化されたエラーを即座に返し、Agentが次のツール呼び出しで即座に自己修正できるようにします。

## 4. サブエージェントとの連携とエラーリカバリ (Interactive Trigger)
### 4.1 メッセージングによる報告フロー
サブエージェント（Worker）は、DBのタスク状態を `COMPLETED` または `FAILED` に更新した後、呼び出し元のフロントAgentに対して **メッセージ通信（send_messageツール等）** を用いて直接結果を報告します。フロントAgentはそれを受け取り、最終的な成果をユーザーへチャットで報告します。

### 4.2 シンプルなエラーリカバリ
サブエージェントがハングアップした場合等の高度な自律的Watchdogは導入しません。もしWorkerがクラッシュして反応がなくなった場合、ユーザーとフロントAgentの対話の中で「Workerの反応がないため、エラーログを確認して再起動します」といった形で、チャットベースのトリガーで安全にリカバリを行います。
