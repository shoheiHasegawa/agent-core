# 03. ルールの引き算計画 (Final)

## 1. 概要
このドキュメントは、旧来の `progress.md` ファイルベースの状態管理から新しい Task Registry へ移行する際、`agent-core` ワークスペース全体のどのルールを削除、または変更するかを詳細に定義します。
3回にわたるサブエージェントのピアレビューを経て、品質ゲート（`make check-all`）の維持を保証しつつ、無駄な認知負荷を削減します。

## 2. 対象ファイルと修正内容

### 2.1 `agent-core/AGENT.md`
**現在のAS-IS**: LLMに対して手動で `progress.md` を更新するよう指示している（ソフト制約）。
**提案するTO-BE (引き算)**:
- **削除**: 手動でのファイル更新指示を削除します。
- **追加**: 「タスク状態の更新は、Agentが手動でCLIを叩くのではなく、必ず `tools/manage_agent_task.py` 等の公式ツールチェーンを経由して自動的にDB（Task Registry）と同期させること。」

### 2.2 `agent-core/skills/session-manager/SKILL.md`
**現在のAS-IS**: 自然言語によるマークダウンファイル（`progress.md`）の読み取りと、チェックボックスの更新指示が含まれており、Handoffプロトコルもファイルの差分（diff）に依存しています。
**提案するTO-BE (引き算)**:
- **削除**: マークダウンのチェックボックス操作に関連するすべての指示を削除します。
- **修正 (重要)**: Handoff プロトコルを再定義します。「Handoff は `manage_agent_task.py status` がスタックしたタスクゼロを返し、**かつ必須の品質ゲートである `make check-all` がパスした**場合のみ許可される。」（品質ゲートは厳密に保護・維持されます）。

### 2.3 `agent-core/GEMINI.md` と Leave No Trace 原則の整理
**過去の監査（Loop 4.3）での誤検知について**:
- 以前の監査で「新しいDBファイルをインフラ層（プロジェクトルートや `core-service/data`）に置くことは、`GEMINI.md` の Rule 5（一時ファイルは `scratch/` のみに置け）という『Leave No Trace』原則に違反する」という指摘がありました。
- **再調査の結果**: 既存のインフラDB（`you_inc_ops.db` 等）は既にプロジェクトルートに配置されており、これらは「一時ファイル（ゴミ）」ではなく「システム永続データ（インフラ）」として扱われています。
- したがって、Rule 5 が禁じているのはあくまで「不要な一時ファイルの散らかし」であり、Task RegistryとしてのDB配置はルール違反には該当しません。
- **結論**: `GEMINI.md`（憲法）をわざわざ改正（修正）する必要はありません。システム永続データとして適切に管理（必要なら.gitignore等で運用）すれば問題ありません。
