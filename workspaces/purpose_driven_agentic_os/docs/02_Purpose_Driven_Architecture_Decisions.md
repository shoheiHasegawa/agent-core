# 目的ドリブン・アーキテクチャへの再定義 (Phase 1-4)

## 1. 背景と課題 (Why)
Agentic OS の運用と拡張を続ける中で、エラーを恐れるあまり「Workerエージェントには推論させず、ルールを機械的にこなさせる」という設計方針（RPA化）が進行した。
この結果、以下の問題が発生した。
*   **メタ認知（Why）の喪失**: Agentが「そもそもこの実装は意図に沿っているか？」という問いを捨て、文字通りのルールを満たすだけの置換ボットに劣化。
*   **部分最適（Reward Hacking）の横行**: 手段の目的化が起き、不必要なコードの生成や、ドメインの文脈を無視した過剰な共通化が頻発。
*   **依存の逆転**: ルールブック（JITドキュメント）自身が「Workerから呼ばれた場合は〜」と呼び出し元を意識するようになり、責務が崩壊。

確実性と創発性はトレードオフではない。AIの最大の武器である「推論（Why）」を殺さずに、かつ暴走を防ぐためのアーキテクチャの再定義が必要となった。

## 2. 決定事項1: ルールの 5W1H 階層分離 (3-Layer Architecture)
手段（HOW）が一人歩きするのを防ぐため、ドキュメントの責務を3層に完全分離した。
1. **`GEMINI.md` (憲法 / Layer 1)**:
    *   【大局の WHY】（ユーザーの自己成長の最大化）と【絶対の WHEN/WHERE】（破壊防止、境界）のみを記述。ドメイン依存のHOWは排除。
2. **`AGENT.md` (責務 / Layer 2)**:
    *   各空間の【WHO（ロール）】と【大局の WHAT（対象ドメイン）】を定義。
3. **`SKILL.md` (手順 / Layer 3)**:
    *   特定のタスクを実行するための【具体的な HOW】と【ミクロな WHY/WHAT】を定義。

## 3. 決定事項2: メタ認知における「広さと深さ」の分離 (Role Separation)
Workerから推論を奪うのではなく、ロールに応じて推論の**方向性**を分けることで暴走を防ぐ。
*   **Orchestrator (広さの推論)**: ドメイン境界を越え、「そもそもこのタスクやルールは妥当か？」「ルールが陳腐化していないか？」を問う。
*   **Worker (深さの推論)**: 与えられたルールを疑うことはせず（絶対の前提とする）、「実装がルールの真の意図に合致しているか？」「ドメイン特有の異常系は他にないか？」という制約内で深く推論する。

## 4. 決定事項3: JITルールにおける依存逆転の排除 (Pure JIT Rules)
JITロードされるルール（`docs/rules/` 等）自身に、「Workerから呼ばれた場合は〜」といった呼び出し元の都合を記載することを禁止した。
*   ルールは純粋な「防護ネット（Floor）」と「思考の踏み台（Trampoline）」の提供に徹する。
*   それをどう解釈・実行するかは、呼び出し元である `SKILL.md` のプロンプト（HOW）側で制御する。

## 5. 決定事項4: プロポーザル駆動 (Zero-Shot Executionの禁止)
確実性と創発性の両立のため、HOWをガチガチに固めることはしない。
*   **「WHY（目的）」** と **「Test（検証条件・終了条件）」** のみをユーザーと厳密に契約（合意）する。
*   その間の **「HOW（過程）」** は、完全な推測の余地（ブラックボックス）としてAgentの創発性に委ね、防護ネット（LinterやCI）で安全性を担保する。

## 6. 実装ログ (Implementation Log)
本決定に基づき、以下のリファクタリングを実施・完了した。
*   `GEMINI.md` の改訂（エラーリフレクション原則、Handoff Protocolの復元と統合）。
*   全リポジトリの `AGENT.md` の刷新（Mission/Vision/Value 形式でのWHO/WHATの定義）。
*   全18個の `SKILL.md` ファイルの完全リファクタリング（HOWのパージ、JITロードの徹底、Workerへの「深さ」の推論の再許可）。
*   JITドキュメント（`sdd_tdd_heuristics.md` 等）からの依存逆転記述（Warning）の全削除。
