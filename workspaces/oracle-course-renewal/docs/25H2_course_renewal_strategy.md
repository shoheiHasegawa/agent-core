# 25下期 勉強会リニューアル戦略・思想・意思決定正本 (Strategy & Philosophy SSOT)

## 1. 根本思想（WHY）：なぜ今、この勉強会が存在するのか？

### 1.1 「月1回×2時間×6ヶ月」というフォーマットの真の価値
- **短期集中（1〜2ヶ月）でやるべきこと**:
  - 資格試験（黒本等）の暗記、ツールの操作手順、フレームワークの使い方。これらは短期集中で自習すべきものであり、月1回の勉強会で暗記をやらせても定着せず、時間軸として破綻している。
- **半年間（長期・低頻度）だからこそ起きる「認知的変容」**:
  - 月1回の講義で**「新しいレンズ（視座・設計思想）」**を渡される。
  - 次の1ヶ月間、受講生は現場業務の中でAIを使い、コードを書きながら**「あ、勉強会で言ってたのはこれのことか！」と何度も反芻（咀嚼）する**。
  - 6ヶ月かけて、エンジニアとしての**「世界の解像度（アーキテクチャのものの見方）」が不可逆的にアップデートされる**。

---

### 1.2 AI時代における組織の地殻変動と若手の生存戦略
AI（Cursor, Claude, ChatGPT等）がコード、SQL、構築手順を一瞬で生成する時代において、エンジニアの役割構造は不可逆的に変化した。

```text
【これまでの構造】
シニアエンジニア（要件定義・アーキテクチャ設計・レビュー）
      │ 指示・検収
      ▼
ジュニアエンジニア（実装・コーディング・作業手順の実行）

───────────────────────────────────────

【これからの構造（AI時代）】
シニアエンジニア（全体統括・事業価値と技術の接続）
      │
ジュニアエンジニア ──★【AIに対する「シニア」としての振る舞いが必須】
      │ （要件定義・設計指示・レビュー・検収）
      ▼
      AI（超高速な実装・生成・コーディング）
```

- **ジュニア層の階層上昇**:
  - 実装工程はAIが担うため、実務1〜3年目のジュニアであっても、**「AIという超高速だが責任を取れない部下」を持つシニアとしての役割（設計指示・レビュー・検収）**を強制的に求められる。
- **レビューできないジュニアの存在危機**:
  - もしジュニアがAIに作らせたものを自分でレビューできず、ブラックボックスのままシニアに横流しするなら、シニアにとっては「ジュニアを挟むコスト（伝言ゲーム＋人件費）が無駄」となり、直接AIに指示を出した方が速い。
  - すなわち、**「AIの成果物をレビューできないエンジニアは、現場から存在意義を失う」**。

---

### 1.3 学ぶべき対象のシフト：HOW（手順・パラメータ）から WHY（設計思想とレビュー観点）へ

| 価値が暴落したもの（AIができる / 無駄） | 一生モノの価値を持つもの（人間にしかできない / 必須） |
| :--- | :--- |
| ・SQL構文や個別パラメータ名の暗記<br>・環境構築の手順やコマンドのなぞり<br>・「INDEXとは何か」という用語解説 | **・「なぜその設計になっているのか」という思想（WHY）**<br>・**「何を気にしなければならないか」というレビュー観点の分母**<br>・**「なぜこのINDEX設計が必要なのか」という判断軸** |

- **観点（分母）さえ持っていれば、AIを最強のレビューワーとして使役できる**:
  - AIに「レビューして」と漠然と頼んでも意味がない。しかし、「更新頻度とB*Treeの書き換えコストの観点でレビューして」「デッドロックの観点でレビューして」と**観点をプロンプトとして渡せば、AIの品質担保は極めて容易になる**。
  - だからこそ、人間が身につけるべきはパラメータの暗記ではなく**「観点（分母）の網羅性」**である。

---

### 1.4 なぜ「Oracle Database」を題材にするのか（HOWへの接続）
- **抽象論の罠（初学者の挫折防止）**:
  - 概念や思想だけを抽象的に語っても、実務経験の浅いジュニア層には手触り感がなくイメージが湧かない（認知負荷の爆発）。
- **生きた具体例・世界最高峰の巨大建築としてのOracle**:
  - 大半のエンジニアは「DBをゼロから構築する側」ではなく「DBを使う側（アプリ開発）」である。
  - だが、DBの内部アーキテクチャ（ACID、REDO/UNDO、ロック、バッファ、WAL）は、**「分散システムやWebアプリ設計におけるデータ整合性と性能の普遍的な設計パターン集」そのもの**である。
  - Oracleという完成された巨大建築を解剖することで、**「アプリの都合で決まるインフラ設計」「インフラの制約で決まるアプリ設計」の両利きの視点**を手に入れる。

## 2. 教育工学に基づくシラバス・体験設計（Backward Design）

### 2.1 観察可能な4つの学習目標（GOAL）
1. **【本質の理解】**: DBが担保すべき本質（ACID特性等）と、それを実現する内部構造（WAL、REDO/UNDO、ロック等）を説明できる。
2. **【アプリ⇄インフラ両利きの視点】**: トランザクション境界やクエリの作りがインフラ（メモリ・ディスクI/O・ロック）に与える影響を指摘できる。
3. **【現場トラブルの解決】**: 現場あるあるトラブル（画面白画面、デッドロック、月末バッチ遅延）の根本原因と解決策を選択できる。
4. **【AIレビュー力（観点提示）】**: AIが提示した設計に対し、見落とされたトレードオフ（局所最適の罠）を指摘し、正しいレビュー観点をプロンプトとして提示できる。

---

### 2.2 設問設計のフレームワーク：【AIの局所最適化失敗パターン4大類型】
AIはデタラメな嘘をつくのではなく、**「局所的には100点だが、全体アーキテクチャやトレードオフを無視した大惨事の正論」**を自信満々に吐く。この失敗パターンを設問に組み込む。

| AIの失敗パターン | AIがやりがちな提案（局所100点） | 見落とされた全体視点（全体0点） |
| :--- | :--- | :--- |
| **① トレードオフの無視**<br>（局所性能の追求） | 「検索が遅いので全カラムにINDEXを貼りましょう！」 | 毎秒の大量INSERT/UPDATEで**B*Treeの更新I/Oが激増し、本番の書き込みが死ぬ**。 |
| **② 責務境界の無視**<br>（アプリで無理やり解決） | 「DBの外部キー制約は重いので外して、アプリコードで整合性をチェックしましょう！」 | 直接SQL実行やバグで**データ不整合（孤立レコード）が紛れ込み、二度と直せなくなる**。 |
| **③ 同時実行（時間軸）の無視**<br>（単一ユーザー視点） | 「残高チェックして残高があれば引き落とすロジックを書きました！（SELECT ➔ UPDATE）」 | 2人が同時に実行すると**残高がマイナスになる（レースコンディション・ロック欠落）**。 |
| **④ 異常系・物理現実の無視**<br>（ハッピーパス思考） | 「データ保存を非同期にして、即座に応答を返すようにしました！」 | サーバーが電源断した瞬間、**メモリ上のデータが蒸発して消える（永続化・耐久性の欠落）**。 |

## 3. 全6回 カリキュラム詳細（現場あるあるシナリオ ＆ ワーク形式のメリハリ）

全回ハンズオンに縛られず、**「設計・議論が生きる回はグループワーク（レビュー会議）」**、**「物理現象を見ないと納得できない回は実機実験」**とメリハリをつける。

| 回 | 講義タイトル | 現場トラブルシナリオ ＆ 学ぶWHY | 後半ワーク形式（30分） |
| :---: | :--- | :--- | :--- |
| **第1回** | **【データと整合性】**<br>〜なぜExcelではなくDBなのか？ 設計の土台とセキュリティ〜 | **シナリオ**: ECサイトで注文はあるのに配送先が消えて発送できない。<br>**WHY**: ACIDの「C（一貫性）」、正規化、制約（PK/FK/NOT NULL）、最小権限の原則（アプリにDBA権限を渡すな）。 | 👥 **【グループワーク回（レビュー会議）】**<br>AIが出したECサイトのテーブル定義をチェックシートで事前個人メモ ➔ チームで粗探し発表。 |
| **第2回** | **【アプリとDBの境界線】**<br>〜どうやって繋がり、なぜ切れるのか？ 接続とセッション〜 | **シナリオ**: 朝9時のアクセス集中でDBは動いているのに画面が真っ白に。<br>**WHY**: リスナーの役割、名前解決、コネクションプール枯渇、セッションとプロセスの違い。 | 🧪 **【実機ハンズオン回】**<br>リスナー停止で新規は `ORA-12541` 拒絶されるが、接続中セッションは普通に動く現象を目撃。 |
| **第3回** | **【速さと安全の両立】**<br>〜なぜメモリが飛んでもデータは消えないのか？ 永続化の奇跡〜 | **シナリオ**: 決済中にサーバーの電源プラグが引っこ抜けた！ データはどうなる？<br>**WHY**: メモリ（SGA）とディスクの役割、WAL（ログ先行書き込み）、REDO（耐久性）とUNDO（過去スナップショット）。 | 🧪 **【実機ハンズオン回】**<br>ターミナルAの未コミット更新をターミナルBで見ても見えない（UNDO）。強制KILL後のインスタンスリカバリ（REDO）。 |
| **第4回** | **【同時実行とロックの力学】**<br>〜2人が同時にボタンを押した時、現場で何が起きるか？〜 | **シナリオ**: 在庫1個の限定商品を2人が同時に購入して在庫がマイナスに。<br>**WHY**: トランザクション境界、分離レベル、行ロック・表ロック、デッドロックの発生機構、MVCC。 | 👥🧪 **【ペア議論 ➔ 実機実証】**<br>どうすればデッドロックが起きるかペアで予想 ➔ 実際に2つのターミナルでぶつけて `ORA-00060` 発生！ |
| **第5回** | **【性能監視と耐障害性】**<br>〜100万件で遅いクエリの見抜き方と、死んだDBの救い方〜 | **シナリオ**: 毎月の給与計算バッチがデータ増加でタイムアウトして終わらない。<br>**WHY**: B*Tree INDEXの動作原理とトレードオフ、実行計画（Explain Plan）、アプリ×インフラの性能監視（CPU/IO/待機）、バックアップリカバリ。 | 🧪 **【実機ハンズオン回】**<br>100万件テーブルでINDEXなし `FULL SCAN`（数秒）➔ INDEX作成で `RANGE SCAN`（一瞬）の激変！ 逆にINDEX過多でのINSERT激遅を計測。 |
| **第6回** | **【総括と総合演習】**<br>〜AIの仕事をレビューするシニアの視座へ〜 | **シナリオ**: 全5回のアーキテクチャ総復習 ＆ AI模擬レビュー総合演習。<br>**WHY**: 知識を確信に変え、現場でAIに適切なレビュー観点を提示できる自信を確立する。 | 📝 **【期末まとめテスト（全20問）】**<br>前半：アーキテクチャ・チートシート総復習（35分）<br>後半：総合試験（45分）＋ その場解説（40分） |
