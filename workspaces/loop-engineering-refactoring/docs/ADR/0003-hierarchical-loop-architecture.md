# ADR 0003: 階層的ループエンジニアリングとJIT知識注入

## Status
Accepted

## Date
2026-08-13

## Context (課題・As-Is)
- これまで `sdd-loop-orchestrator` などの巨大なSKILLが、要件定義から実装、自己検証までのすべてのループを単一のプロンプト内で管理しようとしていた。
- その結果、Agentのコンテキストが溢れ、設計原則（DDD等）やディレクトリ構造のルールが無視される事態（JIT Routingの破綻）が発生していた。

## Decision (合意事項・To-Be)
1. **ルールのJIT (Just-In-Time) 注入と分離**
   - SKILL内に質問スタイルやドメイン固有ルールをハードコードすることを禁止する。
   - すべての制約は `docs/rules/*.md` (Heuristics) としてテキストファイル化し、`/grill-me` 実行時や Worker SKILL の実行時にパス指定で動的に読み込ませる（憑依させる）。
2. **3層の階層的ループ (Hierarchical Loop) アーキテクチャ**
   - 現実の業務プロセスに合わせ、ループを以下の3層に分離して管理する。
   - **Macro-Loop (第1階層: フロー移行)**
     - 管理: `tasks/progress.md` ＋ 人間のトリガー（`@session-manager 次へ`）
     - 対象: 「設計」→「実装」といった大きなフェーズ移行。迷子を物理的に防ぐ。
   - **Meso-Loop (第2階層: 実務・自己完結)**
     - 管理: 純化されたWorker SKILL内の `invoke_subagent` (マイクロループ)
     - 対象: TDDのRed→Greenなど。Workerが自立的にテストAgentを呼び、OKが出るまで内部で回す。人間は介入しない。
   - **Ad-hoc Loop (第3階層: 臨時の高度な議論)**
     - 管理: ネイティブコマンド `/teamwork-preview`
     - 対象: 設計の客観的評価など、一時的に複数Agentの議論が必要な場合に人間が呼び出す。

## Consequences (結果)
- ループの規模に応じて「人間＋ファイル」「Worker内部委譲」「ネイティブ機能」を使い分けることで、プロンプトのコンテキスト溢れを完全に防ぎつつ、複雑な自動化（オーケストレーション）を維持できる。

## Notes for Second Brain
- このアーキテクチャにより、Agentは常に「今やるべき極小のループ」と「それに必要な極小のルール」だけを脳（メモリ）にロードして作業できるようになる。これが作業品質を最大化する鍵である。
