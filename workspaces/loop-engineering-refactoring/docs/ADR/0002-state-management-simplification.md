# ADR 0002: 状態管理の簡素化（DB構築の破棄とMarkdownへの回帰）

## Status
Accepted

## Date
2026-08-13

## Context (課題・As-Is)
- 前回のプロジェクト（`improvement-agentic-os`）において、Agentがルールの読み込みをサボる（JIT Routingの破綻）問題や、状態管理の忘却（Amnesia）といった致命的な課題が正しく特定された。
- これらの課題を解決するためのTo-Beアーキテクチャとして、「SQLiteデータベース（`agent_tasks`）を構築し、複数Agent間のタスク競合をCAS（Compare and Swap）で排他制御する」というインフラ主導の解決策が策定されていた。
- しかし、DB駆動に切り替えても、Agentの実装フェーズにおける作業品質（ディレクトリ構造や設計方針の遵守）は向上しなかった。

## Decision (合意事項・To-Be)
1. **DB駆動（インフラ側）のアプローチの破棄**
   - SQLiteを用いたタスクキュー（`agent_tasks`）および排他制御（CAS）の構築案は破棄する。
2. **Markdownによる状態管理（progress.md）への回帰**
   - 状態（現在地）の永続化は、これまで通りワークスペース内のフラットなMarkdownファイル（`tasks/progress.md`）で行う。
3. **競合（Race Condition）の排除手段の変更**
   - DBのロック機構で競合を防ぐのではなく、**「人間が定型コマンド（トリガー）を引いた時のみ、直列で1ステップだけAgentを動かす」という運用ルール**によって、システム的に複数Agentが同時にファイルを奪い合う状況そのものを発生させなくする。

## Rationale (選定理由)
- **真のボトルネックは「Agentの認知負荷」であるため**: 品質低下の根本原因は「タスク競合」ではなく、「プロンプトが複雑すぎてAgentのコンテキストが溢れていること」にある。インフラをDBに変えてもAgentの脳の負担は減らないため、品質は上がらない。
- **特効薬は「ワークフローの直列化」**: 人間が直列でトリガーを引く「半自動スタイル」を採用すれば、DBのような堅牢な仕組みを持たなくても、単純なMarkdownの読み書きだけで100%確実に状態を管理できる。インフラの過剰エンジニアリング（Over-engineering）を避け、Native-firstなアプローチで根本解決を図るため。

## Notes for Second Brain
- 過去の `improvement-agentic-os` における「課題の特定（As-Is）」は完璧であったが、解決策（HOW）の方向性が重厚長大に向かっていた。
- 今回の決定により、「課題はプロンプト・ワークフローの断捨離で軽く解決する」というパラダイムシフトが完了した。
