# You_Inc Business Activity Inventory (業務棚卸しと介入ポイント)

You_Incは単なるシステム開発プロジェクトではなく、「社長（人間）」と「秘書（Agent）」が協調して回す**パーソナル・オペレーティング・システム（ライフマネジメント基盤）**です。
`data_flow.md` や `system_overview.md` のアーキテクチャから、You_Incの活動（バリューストリーム）は以下の4つの巨大なサイクルに分類されます。

---

## 1. You_Incの4大バリューストリーム（企業活動サイクル）

### A. 日次運用サイクル (Daily Operational Flow - 秘書業務)
社長の日常のタスク管理、スケジュール調整、実績の回収を行う「基幹業務」。
*   **A-1. 日中のアイデア投入 (Mobile Capture)**: 社長がMobile Vaultに思いつきを投下。
*   **A-2. 夜の棚卸し (Night Phase / Triage)**: 秘書AgentがInboxを覗き見し、社長と壁打ちしてタスク（SQLite）として登録するかを仕分ける。
*   **A-3. 朝の計画生成 (Pipeline Phase)**: システムが翌日の計画（Briefing）を生成し、Google Calendarと同期する（完全自動）。
*   **A-4. 実績回収 (Reverse Recovery)**: 社長がMobileでチェックした完了実績をシステムが自動回収し、DBを更新して証跡を消す（Leave No Trace）。

### B. ナレッジマネジメント (Knowledge Harvesting - 図書館業務)
プロジェクトの経験や日々の雑記から、普遍的な知識（Second Brain）を抽出する業務。
*   **B-1. 学びの投函**: 実行完了したワークスペースから `20_Sense_Making` へ教訓を投下。
*   **B-2. Zettelkasten 蒸留**: Socraticな壁打ち（人間との対話）を経て、美しいMarkdownの `Permanent_Notes` として永続化する。

### C. 自律修復・イベント処理 (Autonomous Healing - 運用保守)
システムに生じたエラーや通知を、Agentが自律的に処理するフロー。
*   **C-1. Event Bus処理**: パイプライン等で生じたエラーが `agent-core/events/` にパケットとして投函され、それをAgentが検知して修復タスク（Inbox化）に繋げる。

### D. 追加機能開発 (System Development - 工場業務)
You_Inc自身の機能（core-serviceやagent-core）を拡張・改修する業務。（※前回の洗い出しの中心）
*   **D-1. 仕様策定 (SDD)**: 要件定義の壁打ちと `spec.md` 作成。
*   **D-2. 実装ループ (TDD)**: 仕様に基づく自律的な実装とテスト。

## 2. 人間（社長）の介入ポイントとAgentの役割定義

この「企業全体の活動」を見たとき、社長（あなた）の介入ポイントはさらに明確になります。社長は**「意思決定（壁打ち）」と「現場の実行（チェック）」のみ**を行い、中間の管理業務はすべてシステムが担います。

| ドメイン | 業務 | 👨‍💼 人間（社長）の介入ポイント | 🤖 Agent / システムの役割 |
| :--- | :--- | :--- | :--- |
| **A. 日次運用** | 夜の棚卸し (Triage) | **[高]** Agentの提案に対し「やる/やらない」のジャッジと合意を行う。 | 未処理Inboxを提示し、タスクをDBへ登録し、ゴミを消す。 |
| | 朝の計画・同期 | **[無]** （関与しない。朝起きてBriefingを見るだけ） | Cron/Jobとして働き、Briefing生成とGCal同期を行う。 |
| | 日中のタスク実行 | **[高]** 実際にタスクをこなし、Mobileの `[x]` にチェックを入れる。 | （システムは待機） |
| | 実績回収 | **[無]** （関与しない） | Mobileの `[x]` をパースしてDBのWorklogを更新し、ファイルを消す。 |
| **B. 知識** | ZK 蒸留 | **[中]** 「この文脈でノート化して」と対話し承認する。 | 過去の文脈を読み取り、指定フォーマットで原稿を生成する。 |
| **C. 保守** | Event処理 | **[低]** 最終的なコード修正の承認など。 | エラーパケットを検知し、原因を分析して修正案を提示する。 |
| **D. 開発** | SDD (要件定義) | **[高]** 「何を作りたいか（WHY/WHAT）」を壁打ちで定義する。 | 仕様の穴（エッジケース等）を指摘し、`spec.md` を執筆する。 |
| | TDD (実装ループ)| **[極低]** 「次へ」と**トリガー**を引き、完了報告をレビューするだけ。 | `progress.md` に従い、ディレクトリ構造を守ってコードを書く。 |

## 3. インターフェース（SKILL）設計への落とし込み

You_Incの全貌を俯瞰すると、SKILL（AIの振る舞い）として人間が明示的に呼び出す必要があるのは、**「介入度【中〜高】で、かつ人間とのリアルタイムな対話（壁打ち）が必要な業務」**にほぼ限定されます。

1.  **システム自動実行（介入度 無）**: 朝のパイプラインや実績回収は、バッチ処理（Cron/Job）でありSKILLとしては呼ばれない。
2.  **壁打ち特化（介入度 高）**: 「夜の棚卸し」「SDD」「ZK蒸留」などは、`/grill-me` によるネイティブな対話とHeuristics（問いのルール）で代替可能。
3.  **定型作業のルーティング（介入度 低）**: 「TDD実装」などは、`@session-manager 次へ` という定型コマンドと、純粋なルールファイル（Worker SKILL）の組み合わせで処理される。
