# 🛡️ Agent Anti-Patterns & Precedents Catalog (失敗パターン＆前例集)

## 🎯 本ドキュメントの存在目的 (WHY)
過去のプロジェクトおよびスキル群の運用から得られた「AIエージェントが陥りやすい失敗パターン（`[EXP-XX]`）」と「社長の意思決定の前例（`[PREC-XX]`）」を実践カタログとして蓄積し、同じ失敗の再発防止と前例ベースの自律判断（Tier 1/2）を実現するため。

---

## Part 1: 開発・TDD・レビュー・引き算における失敗パターン (Engineering Anti-Patterns)

### [EXP-01] 実装コードを見てテストを書く「確証バイアス（後付けテスト）」
- **失敗の現象**: テスト作成者が既存のプロダクションコード（実装詳細）を読んでからテストを書くと、実装のバグや間違った分岐をそのまま追認するテスト（トートロジー）を書いてしまう。
- **対策（教訓）**:
  - `tdd-red-worker` は **プロダクションコードの実装中身を閲覧・編集してはならない（情報隔離）**。
  - 必ず `spec.md`（仕様契約）と公開インターフェース（シグネチャ・DTO・Port定義）のみを見て、「何が起きるべきか」のテスト（Red）を書け。

### [EXP-02] 「先回り実装」と「手続き型ファットUseCase」によるDDD崩壊
- **失敗の現象**:
  1. `tdd-green-worker` が `spec.md` を読んで、まだテストで要求（アサート）されていない将来のシナリオまで一度に先回り実装し、カバーされないデッドコードを生む。
  2. 外側の結合テスト（Integration）を最短で通そうとして、UseCase の中にすべての `if` 分岐や計算ロジックをベタ書きし、Domain モデルが単なるデータ入れ物（貧血ドメインモデル）になる。
- **対策（教訓）**:
  - テストでアサートされていないビジネスロジックの先回り実装は厳禁。
  - **Pass 2（2周目：引き算リファクタリング）** において、UseCase に書かれた条件分岐・バリデーション・計算ロジックを必ず `Domain` 層（Entity / ValueObject）のメソッドへ抽出し、UseCase を薄いオーケストレーターに保て。

### [EXP-03] 上流（`spec.md`）の小さな曖昧さが下流で100倍に増幅する（Bullwhip Effect）
- **失敗の現象**: `spec.md` のレビュー時に「少し言い回しが曖昧だが意図は分かるから `IMO` / `SHOULD` でよい」と見逃した結果、コンテキストを持たない後続の `tdd-red-worker` と `tdd-green-worker` が別々の解釈をして実装し、結合時に全手戻りになる。
- **対策（教訓）**:
  - **上流工程（`spec.md`・インターフェース定義）における「2通りに解釈できる曖昧さ」「境界条件の未定義」「用語の揺れ」は、見た目がどれほど軽微でも後続への波及度が最大であるため、無条件で 🔴 `MUST`（Blocker）として即修正せよ**。

### [EXP-04] レビュアーの「無限指摘バイアス」による過品質・ループ発散
- **失敗の現象**: 独立レビュアーに「問題がなくなるまでレビューせよ」と指示すると、重大な問題がゼロになった後も「変数名がもっと良くできる」「将来のために抽象化すべき」と毎回異なる観点から指摘をひねり出し続け、ループが収束せずコードが複雑化する。
- **対策（教訓）**:
  - レビューの分母は事前固定した `spec.md` と指定ルールのみとし、後出しの観点追加を禁ずる。
  - 差し戻し（Reject）できるのは 🔴 `MUST` のみとし、🟡 `SHOULD` は Pass 2 で1回まとめて処理、🟢 `IMO` は切り捨ててループを確実に閉じよ。

### [EXP-05] チャット返り値への全文出力によるコンテキスト汚染
- **失敗の現象**: サブエージェント（ワーカーやレビュアー）が数百行のコード差分やレビューレポート全文をチャットメッセージとして親（リーダー）に返すと、親のコンテキストウィンドウが数ループで圧迫され、指示忘れやハルシネーションを引き起こす。
- **対策（教訓）**:
  - 詳細な出力はすべてファイル（`git diff`, `scratch/review_report.md`, `scratch/research_report.md`）に書き出し、チャットには **「出力ファイルパスと1〜3行の合否ステータス（MUST件数等）」のみ** を返せ（Pass-by-Reference）。

### [EXP-06] Zettelkasten 蒸留における「AIの綺麗な要約」による熱量（Why）の消失
- **失敗の現象**: 社長との壁打ちログをAIが Permanent Note にまとめる際、教科書的で無難な一般論に丸めてしまい、「なぜ社長がその課題にぶつかり、どんな葛藤の末にその洞察に至ったか」という生々しい熱量（エントロピー）が消えてしまう。
- **対策（教訓）**:
  - `zk-distiller` はAI特有の平滑化された要約を避け、社長自身の言葉・具体例・対比構造（「一見〇〇に見えるが、実は△△である」）をそのまま核として残せ。

### [EXP-07] チームリーダーの「自分で書いた方が早いバイアス」による委譲スキップと自己レビュー
- **失敗の現象**: `team-leader` に実装タスクを委譲した際、リーダーがサブエージェント起動のオーバーヘッドを嫌い、自らテストと実装の両方を直接書いて自己レビューで完了報告してしまう（結果として情報隔離 `[EXP-01]` が破られ、確証バイアスが再発する）。
- **対策（教訓）**:
  - ドメインロジックや新規機能追加（SDD×TDD対象）では、`team-leader` が `.py` を直接編集することを禁じ、必ず `tdd-red-worker`（`Model="flash"`）と `tdd-green-worker`（`Model="flash"`）を起動させよ。
  - また、いかなる場合も完了判定前には必ず別サブエージェントとして `compliance-reviewer`（`Model="pro"`）を起動させ、トランスクリプト上の `invoke_subagent` 実行証跡と `scratch/review_report.md` の出力をもって監査完了とせよ。

### [EXP-08] 使い捨て Workspace への永続成果物 docs 放置アンチパターン
- **失敗事象**:
  - `workspaces/<epic>/docs/` に設計書やプロンプト正本を作成していたため、`make ws-harvest` 後に更地化（`ws-clean`）すると大事な成果物が消滅する危機に瀕した。
- **根本原因**:
  - 「Workspace（仮設足場）」と「Worktree（PR対象の納品物）」の境界の認識が甘く、仮設 Workspace 直下に `docs/` フォルダが存在したことで一時メモと永続ドキュメントの置き場所が混同された。
- **再発防止策（前例）**:
  - 永続成果物としてのドキュメントは、最初から PR 対象となるリポジトリ（`worktrees/<repo>/docs/`）の正しい配置場所にコミットせよ。
  - 使い捨ての workspace 直下に `docs/` を作ってはならない。作業中の一時的な議論メモ・比較表・調査レポートはすべて `scratch/` に配置し、クローズ時に破棄せよ。

### [EXP-09] 手足を持たない Areas へのシステム HOW 混入（依存汚染）の罠
- **失敗事象**:
  - `second-brain/10_Areas/04_Life_Systems` に「Workspaceで実行する」「タスクは別のトラッカーで管理する」といったシステムの運用手順（HOW）が混ざっていたため、タスク管理基盤を改修した際にメンテ漏れ・二重管理の危機に瀕した。
- **根本原因**:
  - クリーンアーキテクチャの「単方向依存ルール（Dependency Inversion）」の違反。最内周エンティティ（社長の人生基準 Areas）が最外周インフラ（ツール・Workspace）を直接参照（依存汚染）していた。
- **再発防止策（前例）**:
  - **`agent-core` は `Areas` を知っているが、`Areas` は `agent-core` を知らない。**
  - `10_Areas` からはツール名や運用手順を完全に引き算（Delete）し、純粋な「生き方の基準（Policy）」のみに純化せよ。システム運用手順（HOW）はすべて `agent-core` に一元化せよ。

### [EXP-10] AI の「足し算バイアス」によるドキュメント腐敗と時系列ノイズ混入
- **失敗事象**:
  1. ワークスペース内の作業ドラフトを捨てるのを恐れ、無批判に `agent-core/docs/tasks_sync/` という新規フォルダを作ってパッチ当てしようとした。
  2. プロジェクト進行中の議論ログや移行計画（「—【確定】」「旧〇〇を廃止」「アジャイル実装ロードマップ」などの時系列情報）をそのまま本流の正本（`docs/architecture.md` 等）にコピペし、Timeless SSOT が過去との差分で汚染された。
- **再発防止策（前例）**:
  - **新規フォルダを乱造するな、既存正本（`architecture.md` / `SKILL.md`）を直接修正せよ（Atomic Update）。**
  - すべての正本ドキュメントは冒頭に必ず「本ドキュメントの存在目的（WHY）」を定義し、`WHY ➔ WHAT ➔ HOW` の順で現在形の事実のみを記述せよ（`tools/audit_skills.py` で機械検証）。

### [EXP-11] AI 時代のデリバリー優先（価値創出）とスコープ保護
- **失敗事象**:
  - Google Tasks 連携基盤（Issue #3）が完成した勢いで、運用フェーズである「Inbox の大掃除」まで同一セッション・同一Issueで引きずろうとした。
- **再発防止策（前例）**:
  - 「動く価値（基盤）」が完成した瞬間に一度切ってデリバリー（PR作成・マージ）せよ。運用開始（大掃除）は基盤構築とは独立した別スコープであるため、次期 Issue へ外出しし、1 Issue 1 PR を厳守せよ。

### [EXP-12] カレンダー終日枠埋め尽くし（Calendar Pollution）アンチパターン
- **失敗事象**:
  - Google Tasks のタスクに安易に期日（due）を設定すると、Google カレンダーの終日枠がToDoで真っ青に埋め尽くされ、スケジュール（Fixed Time）の視認性が完全に死ぬ。
- **再発防止策（前例）**:
  - カレンダー終日枠に表示されるのは **その日の最重要タスク（`⭐️ [Must]` 最大3件）のみ** とする。
  - その他のタスク（Should, Want, Inbox）には Google Tasks の due 属性を設定せず、Notes（詳細）欄のメタデータ（`[deadline: YYYY-MM-DD]`）として退避せよ。

### [EXP-13] Google Tasks API はサービスアカウントで動かない（403 Forbidden）
- **失敗事象**:
  - Google Calendar と同様に `credentials.json`（サービスアカウント）で Google Tasks API を叩こうとして `403 Forbidden` エラーで遮断された。
- **再発防止策（前例）**:
  - Google Tasks の連携クライアントには **OAuth 2.0（User Credentials）** を採用せよ。初回ローカル認可フロー（`tools/authenticate_google.py`）で `token.json` を発行し、リフレッシュトークンで自動更新せよ。

### [EXP-14] 親エージェント（秘書）の「対話の勢いによる直プッシュ」とWorktree隔離スキップ
- **失敗事象**:
  - `second-brain` の「Inbox棚卸し（大掃除）」というトピックタスクにおいて、親エージェント（秘書）が対話の流れの中で自らファイルを編集・削除し、Worktree（`make ws-new`）を切らずに `main` ブランチへ直接コミット＆プッシュ（Direct Push）してしまった。
- **再発防止策（前例）**:
  - 親チャット（秘書）はオーケストレーターに徹し、複数ファイルの削除・構造改革・大掃除を伴うトピックタスクでは、必ず `make ws-new ... REPOS=...` で隔離Worktreeを起動し、完了時に PR 起票 ➔ 独立レビュー（MUST=0） ➔ マージ ＆ 更地化（`make ws-clean`）の物理手順を死守せよ。

### [EXP-15] 過剰な引き算（単一ファイル統合 ＆ WHY の引き剥がし）によるコンテキスト汚染と凝集度崩壊
- **失敗事象**:
  - 「引き算ファースト（Delete First）」を適用する際、① Workspace 内のすべての状態・目標・教訓ファイルを単一のファイル（`state.json` 1個）に統合しようとし、また ② `SKILL.md` やルールから「WHY（なぜこの制約が必要か）」を完全に削ぎ落として別ファイルへ分離しようとした。
- **根本原因**:
  - 「ファイル数や文字数を減らすこと」自体が目的化し、**コンテキストエンジニアリング（誰が・いつ・どの粒度で読み込むか）** と **変更の凝集度（WHY と WHAT の Locality of Behavior）** の観点が抜け落ちた。
  - アクセスパターンの異なる情報を単一ファイルにまとめると、毎ターン不要な情報まで読み込んでコンテキスト汚染（Attention Dilution）を起こす。また、ルールから WHY を引き剥がすと、後からそのファイルを見た Agent や人間が「なぜこの制約があるのか（消すと何が壊れるか＝チェスタトンのフェンス）」を判断できず、安易にルールを改悪するリスクを生む。
- **再発防止策（前例）**:
  1. **アクセスパターンに基づくファイル分離**: 毎ターン読む短期メモリ（`tasks/context.md`）と、着手・完了時に見る Goal/DoD（`AGENTS.md`）と、一時的な議論・調査置き場（`scratch/`）は絶対に単一ファイルへ混ぜてはならない（統合してよいのは、同じライフサイクルで二重管理になっていた `AGENTS.md` の DoD と `progress.md` のみ）。
  2. **1行 WHY の高凝集保持（Co-located Concise WHY）**: ルールや `SKILL.md` の各制約の直前には、必ず **「1〜2行の鋭い WHY（何を防止するための制約か）」をセットで残せ**。削るべきは「WHY」ではなく、「複数ファイルにコピペされた重複説明文」と「廃止済みのゾンビ資産」のみである。

### [EXP-16] `agent-core/pyproject.toml` における相対パス依存（`../core-service`）による Worktree 隔離破綻
- **失敗事象**:
  - `agent-core` の Worktree（`workspaces/<epic>/worktrees/agent-core/`）内で `make check-all`（`uv run`）を実行した際、`pyproject.toml` に `core-service = { path = "../core-service", editable = true }` という相対パス依存が定義されていたため、3階層深い Worktree からの相対パス解決に失敗して仮想環境構築がクラッシュした。
- **根本原因**:
  - `agent-core` は「業務ロジックを持たず、`Makefile` 経由で `--project $(CORE_SERVICE_DIR)` を指定して `core-service` の CLI を外からキックする（`[PREC-01]`）」設計であるにもかかわらず、旧構成の名残で `pyproject.toml` 自体が `../core-service` に直接結合していた。
- **再発防止策（前例）**:
  - `agent-core/pyproject.toml` は外部リポジトリへの相対パス依存を持たない完全自立構成（`dependencies = []`）に保ち、どの階層の Worktree にマウントされても単体で `make check-all` が完走するようにせよ。

## Part 2: 社長の意思決定・アーキテクチャ判断の前例集 (Executive Precedents)

### [PREC-01] 定型処理・CLIツールの配置場所（`agent-core` vs `core-service`）
- **判断基準（前例）**:
  - **「静的に検証できるもの・定型処理はAgentの推論に委ねずスクリプト（CLI/Linter）化する」**。
  - その際、DBや外部APIやファイル操作を伴う業務CLIツール、およびDIコンテナの組み立ては **すべて `core-service` 側（`src/entrypoints/cli/`, `src/di/`）の公式ツールとして集約** する。
  - `agent-core` 側には業務Pythonコードを置かず、`config/conf.env` と `secret.env` を外から注入して `core-service` の口をキックするだけの極薄構造を保つ。

### [PREC-02] 人間のスケジュール/ToDo と 会社のIssue管理の境界
- **判断基準（前例）**:
  - 社長個人の予定・期限付きタスク・ルーティンは **Google Calendar & Google Tasks**（スマホのGeminiアプリ＆iPhoneウィジェット連携）を正本とし、ローカルSQLiteでの人間タスク管理は行わない。
  - 会社（Agentチーム）が動く開発・改善課題は **GitHub Issues (`gh issue`)** を正本とする。
  - 思考メモ・着想の種は **Obsidian (`Mobile Vault` / `second-brain`)** を正本とする。

### [PREC-03] Antigravity モデル枠（Argon vs Gemini Models）の最適配分
- **判断基準（前例）**:
  - `Gemini 4 Argon` は週次固定枠（5h回復なし）のため、ゼロからの重いアーキテクチャ設計時のみ親チャットで切り替えて使用する。
  - 日常の秘書対話・壁打ちは親チャットの **`Flash (High)`** を基本とする。
  - サブエージェント（`invoke_subagent`）は5時間ごとに高速回復する `Gemini Models` 枠をフル活用し、判断の要である `team-leader`・`compliance-reviewer`・`zk-distiller` には **`Model="pro"`**、実装ワーカー（`tdd-red/green-worker`）には **`Model="flash"`**、非破壊調査（`research-worker`）には **`Model="flash_lite"`** を割り当てる。

### [PREC-04] 大規模アーキテクチャ・仕組み刷新における段階的移行パターン
- **判断基準（前例）**:
  - 組織構造やリポジトリ境界などの大きな仕組みを刷新する際は、一度にすべてを書き換えようとせず、必ず以下の4ステップ（WHY ➔ WHAT ➔ HOW）で段階移行せよ：
    1. **🏛️ 変えると負債になる骨格（WHY / WHAT）の先行合意**: 組織階層、データ境界（SoR）、ブランチ戦略、ループの停止条件など、後から変えると手戻りが大きい骨格を最初に言語化して合意する。
    2. **🛠️ 安全装置・ハーネス（Worktree & 独立CI）の先行構築**: 本流（`main`）を壊さずに実験できるよう、`make ws-new` / `make check-all` の土台を最初に作る。
    3. **📜 思考原則・薄いSKILLの整備と旧資産の引き算**: 新しいルールやSKILLを足すだけでなく、不要になった旧ドキュメント・旧スクリプトを必ず同一サイクルで削除（引き算）する。
    4. **🧪 実タスクを題材にしたE2E試運転と正本（Timeless SSOT）化**: 実際の機能実装を通じてサブエージェント連携を動作検証し、完了後に移行期の時系列ノイズを剥がして `docs/architecture.md`（現在形の正本）へ昇格させる。

### [PREC-05] ワークスペースの完全ライフサイクルとGitHub PRによる恒久アーカイブ
- **判断基準（前例）**:
  - **「ワークスペース（`workspaces/<epic>/`）は仮設足場（Scaffolding）であり、完了後はローカルから完全削除（更地化）する」**。
  - 「捨てるのが怖いからアーカイブフォルダに退避する」のは足し算バイアス（未練）。
  - 作業履歴・レビュー結果・意思決定の変遷は、すべて **GitHub PR のタイムライン・コミット履歴として恒久保存（SoR）** される。
  - したがって、すべての開発は：
    1. `make ws-new` で `agent-core` に `epic/<name>` ブランチを切り、Worktree をマウントして作業する。
    2. 開発完了時は `gh pr create` で PR を作成し、3点ブリーフィングと重要な意思決定根拠を記載して Issue（`Closes #XX`）と紐付ける。
    3. 社長承認で PR をマージする。
    4. マージ後に `make ws-clean` でワークスペースディレクトリを完全削除し、ローカルを常に「作業中の現場のみ」に保つ。

### [PREC-06] `second-brain` の二刀流運用（日常 Direct Push vs トピック Worktree/PR）
- **判断基準（前例）**:
  - `second-brain` に対する「全面的な直接Push禁止」は、思考の摩擦（認知コスト）を増大させ、Obsidianとの同期断絶やロングブランチでのコンフリクトを招くため採用しない（引き算ファースト）。
  - 代わりに、**作業の性質に応じた二刀流運用** を徹底する：
    1. **日常モード（Direct Push）**:
       - 対象: 日常の殴り書き（Inbox）、単発ノートの追記・タイポ修正、単発の Permanent Note 登録。
       - 運用: 思考の摩擦ゼロと即時性を最優先とし、`main` へ直接コミット＆プッシュ（Conventional Commits 必須）。
    2. **トピック / Epicモード（Worktree & PR）**:
       - 対象: 体系的学習（`cca-foundations` 等の集中蒸留）、大掃除・バックログ消化（Inbox棚卸し）、構造改革（全ノートフォーマット変更等）。
       - 運用: GitHub Issue を起票し、`make ws-new EPIC=<name> REPOS=second-brain ISSUE=<num>` で隔離 Worktree を作成。作業完了時に PR（3点ブリーフィング付き）を作成し、即時マージ ＆ `make ws-clean` で更地化して史実を恒久アーカイブする。

### [PREC-07] 情報のライフサイクルに応じた3層記録境界（`scratch/` vs `docs/experiences/` vs `GitHub PR`）
- **判断基準（前例）**:
  - 議論の過程、比較検討、意思決定の根拠をどこに残すかは、**「その情報を後から誰が・いつ使うか（ライフサイクル）」** によって以下の3箇所に明確に振り分ける：
    1. **作業中のみ必要な議論の流れ・ボツ案比較・調査/レビュー詳細 ➔ `workspaces/<epic>/scratch/`**
       - Epic 進行中にセッションを跨いで参照するための仮設領域。結論が出て正本に昇華された後は、`make ws-harvest` / `ws-clean` でローカルから自動破棄する。
    2. **次回以降の別タスクでも再利用する普遍的な判断基準・アンチパターン ➔ `worktrees/agent-core/docs/experiences/` (`[EXP-XX]` / `[PREC-XX]`)**
       - 「なぜその設計判断を下したか」の再利用可能なルール・前例として Git コミットし、次回以降の 🟢 Tier 1 / 🟡 Tier 2 判断の根拠とする。
    3. **そのタスク固有の意思決定の史実・経緯の恒久アーカイブ ➔ `GitHub PR Description`（および Issue）**
       - PR 本文の「3点内省ブリーフィング」に判断根拠のサマリーを記載してマージすることで、ローカルのファイルを肥大化させずに GitHub 上の SoR として永久保存する。
