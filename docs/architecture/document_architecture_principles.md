# Document Architecture Principles (ドキュメントアーキテクチャの原則)

Agentic OS (You_Inc) における、ドキュメントの「責務（書いてよいこと/悪いこと）」と「ライフサイクル（記憶の階層）」を定義するメタ・ガイドライン。
システム全体のFat化や、AIエージェントのコンテキスト喪失（Lost in the middle）を防ぐため、全エージェントはこの原則に従ってドキュメントを配置・更新しなければならない。

---

## 1. 記憶の3層モデル (Document Lifecycle)

You_Incのドキュメントは、その揮発性と役割に応じて3つのレイヤー（短期・中期・長期）に厳密に分類される。

### Layer 1: Short-Term Memory (揮発性の作業デスク)
* **対象**: Antigravity Artifacts (`task.md`, `implementation_plan.md`, `walkthrough.md`)
* **役割**: 現在の「1セッション（1回の会話）」における短期的な思考整理と、ユーザーの即時レビュー（Approve）を得るためのUI。
* **運用**: あくまでWIP（仕掛品）であり、セッション終了時には揮発するものとして扱う。決定事項は必ずLayer 2またはLayer 3に同期（Handoff）すること。

### Layer 2: Mid-Term Memory (動的なプロジェクトルーム)
* **対象**: Epic Workspaces (`agent-core/workspaces/*/tasks/`, `docs/`)
* **役割**: 数日〜数週間にまたがる特定のプロジェクト（Epic）を遂行するための、時系列と文脈（議論の過程）を保持する「Handoff（申し送り）領域」。
* **運用**: AIが入れ替わっても進捗を見失わないための絶対的な外部記憶。プロジェクトが完了するまで動的に更新され続ける。

### Layer 3: Long-Term Memory (不変の真実 / Timeless SSOT)
* **対象**: 各リポジトリ直下の `docs/` (`core-service/docs/`, `agent-core/docs/`), `spec.md`, `second-brain/`
* **役割**: プロジェクト（Layer 2）での実装や議論が完了したのち、**最終的な確定事項（ルール、ADR、仕様）だけを抽出して保存する「法務局・図書館」**。
* **禁止事項**: ここに「時系列」「議論の過程（昨日はA案だったが今日はB案など）」「未確定のTODO」を記載してはならない。AIに最新の仕様をハルシネーションさせないための完全自己完結型（Timeless SSOT）でなければならない。

## 2. 5W1Hの階層分離とドキュメントの責務 (Layered Rules)

Agentが自らの責務を自律的に判断し、手段の目的化（Reward Hacking）を防ぐために、システム全体のルールを「5W1H」の観点で物理的・論理的に分離する。

### 2.1 `GEMINI.md` (Global Constitution / 憲法)
* **担当**: 【大局の WHY】と【絶対の WHEN / WHERE】
* **責務**: 全プロジェクトを超越した普遍的な哲学、AIの思考バイアス抑制（インクリメンタリズム等）、絶対安全ルール（破壊的変更前のコミット等）。
* **禁止事項**: 特定のドメインのルール、ツールの具体的な使い方（HOW）を書いてはいけない。システム全体がFat化するため。

### 2.2 `AGENT.md` (Domain Router / 司令塔)
* **担当**: 【WHO（私は何者か）】と【大局の WHAT（何を成す空間か）】
* **責務**: その空間（ドメイン）の目的とAgentの役割、関連ルール（`docs/` および `rules/`）への**ポインタ（ルーティング）**。
* **禁止事項**: `GEMINI.md` の普遍的ルールとの重複、実装の手順そのものを書いてはいけない。

### 2.3 `SKILL.md` (Execution Procedure / 実行手順)
* **担当**: 【具体的な HOW（手順）】と【ミクロな WHAT / WHY】
* **責務**: 特定のタスクを達成するための純粋な手段（関数）。この層には大局的なWHYは漏れ出さず、「なぜこの順番で手順を踏むのか」という手順自体の理由（ミクロWHY）のみを記載する。
* **禁止事項**: ドメイン知識や設計制約（JSON-Firstで作れ、等）をハードコードしてはならない。制約は `rules/` に切り出し、SKILLからJITロード（DI）させる。

### 2.4 `spec.md` (Timeless SSOT / 仕様の正本)
* **書くべきこと**: 確定したI/O型、エッジケース、インラインのRationale（なぜこの設計になったかの理由）。
* **禁止事項**: 議論の過程、時系列、外部の動的メモへのリンク。

### 2.5 `progress.md` / `task.md` (Dynamic Workflow / Layer 2)
* **書くべきこと**: アトミックに分解されたチェックリスト、現在の状態、次アクション（時系列）。
* **禁止事項**: 永続化すべき仕様やシステムルール。

## 3. ルール純度の維持とガバナンス (Context DI & Governance)

ルールの純度（コンテキスト）を保つため、機能（SKILL）とドメイン知識（docs/rules）の責務を分離し、以下の仕組みで維持する。

### 3.1 ディレクトリ層によるコンテキスト分離（Architecture / Rules / Templates）
ルールの純度とコンテキスト汚染の防止を両立するため、`docs/` 配下の知識領域を「地図」「法律」「型枠」という直交する次元で完全に分離する。

- **`docs/architecture/` (全体把握のための地図)**
  - **役割**: システム全体のアーキテクチャ背景、メタ原則、抽象度の高い全体方針（WHYと大きなWHAT）。
  - **利用フェーズ**: 設計の壁打ち、Epicの初期設計、および成果物の設計レビュー時。
  - **読む主体**: 全体を把握し計画を立てるOrchestrator（Tier 1）や、合憲性を審査するReviewer。

- **`docs/rules/` (具体的な作業の制約 / 法律)**
  - **役割**: 適切な粒度でマイクロ化（チャンキング）された、具体的な作業制約（HOWを縛るもの）。
  - **利用フェーズ**: 実際のタスク（実装やオーケストレーション）を実行する瞬間。
  - **読む主体**: 実際に手を動かす担当Agent。
    - 実装Worker（Tier 2）は「実装の制約（テスト規則、エラーハンドリング等）」を見る。
    - Orchestrator（Tier 1）は「統制の制約（オーケストレーションの作法等）」を見る。

- **`docs/templates/` (フォーマットの型枠 / 雛形)**
  - **役割**: 仕様書（spec.md）やドキュメントを作成する際に埋めるべき「物理的なフォーマット（型）」。
  - **利用フェーズ**: ドキュメントを新規作成する初期化の瞬間。
  - **読む主体**: ドキュメント作成を担当するWorker（`sdd-spec-builder` 等）。純粋な物理フォーマットであるため、思想や制約は持たず、単にコピー元の雛形として機能する。
  - **【テンプレートの設置基準 (When to use templates)】**:
    - **⭕️ 用意すべきケース**: 後続のプロセス（Linter、パーサー、他のAgent）が、**そのドキュメントの「構造・見出し・記述記法」に依存している場合**（例: 必須項目がある `spec.md` や、YAMLフロントマターが必要な `SKILL.md` など）。
    - **❌ 用意しないケース**: 出力が自由記述でよく、人間のための可読性や文脈の保存が目的の場合（例: 設計の壁打ちログ、調査レポート、Zettelkastenのフリー思考ノートなど）。構造をガチガチに固めるとAgentの創発性が失われるため、あえて型枠は用意しない。

**【交差分離の原則 (Cross-Separation)】**
ルールの解像度と自身の責務に応じて、読み込むべきコンテキストを交差的に分離する。

- **Tier 1 (Orchestrator / Reviewer)**
  - **見るもの**: `docs/architecture/`（全体把握）と、自身の作業に必要な `docs/rules/`（統制の制約）。
  - **読まないもの**: Workerに委譲した領域の `docs/rules/`（詳細な実装・コーディング制約など）。これらをJITロードしてはならない。

- **Tier 2 (Worker)**
  - **見るもの**: 自身のタスクに必要な `docs/rules/`（実装の制約）。
  - **タイミング**: 具体的なコードやテストを実装する瞬間。推論リソース温存のため、必要なルールファイル名を直接リンク（静的DI）してJITロードする。
  - **読まないもの**: `docs/architecture/`（大局的な思想背景は、純粋な実装フェーズにおいてはコンテキスト過多となるため原則として読み込まない）。

**【JITロードにおける原則と例外（Static vs Dynamic DI）】**
* **原則**: システム全体として、推論リソース温存と確実性（Deterministic）担保のため、実務や標準オーケストレーションにおける `_index.md` からのクエリ抽出（動的DI）は廃止し、**すべて静的DI（ファイル直接リンク）**とする。
* **例外（ズームアウト特例）**: 意図的なメタ認知の促進や、未知のルール・解決策を探索するための「ズームアウト特化SKILL（大局の守護者・全体俯瞰レビュー等）」においてのみ、例外的に `_index.md` を用いた動的DI（広さの探索）を許可する。

### 3.2 情報の保存則 (Migration Rule)
SKILLから大局の思想やドメイン固有の制約を削除（リファクタリング）する際は、情報欠落を防ぐため必ず以下の移行プロセスを踏むこと。
1. **退避とクロスチェック**: 削除する制約が上位レイヤー（`GEMINI.md`, `AGENT.md`, `docs/rules/` 等）に既に存在するか確認し、存在しない場合は `docs/rules/` の適切なチャンクに追記（退避）する。
2. **ミクロなWHYへの変換**: 削ぎ落としたSKILLには、大局のWHYの代わりに「なぜこの手順を踏むのか（例: 防波堤を守るため）」という手順自体の理由を残す。
3. **JITロードの明記**: SKILL内から静的制約を消す代わりに、必要なルールファイルへの直接リンク（静的DI）を用いたJITロード手順（HOW）を追記する。

### 3.3 Skill Reviewer (司法による検閲)
新しいSKILLの作成や既存SKILLの修正を行う際は、必ず `skill-reviewer` 等の審査Agentを通し、「大局のWHYが混入していないか」「ミクロなHOWに特化しているか」をシステム的に検閲する。
