# Skill Design Principles (SOLID)

Agentic OS (`agent-core`) において、AIエージェントの振る舞い（Skill）を実装する際の絶対的な設計原則を定義する。

## 1. 2-Tier Architecture (オーケストレーターとワーカーの分離)

Skillは、責務に応じて「オーケストレーター層」と「ワーカー層」の2段階に明確に分割すること。

*   **Tier 1: Orchestrator (状態管理とルーティング)**
    *   **責務**: 処理の全体の流れ（Workflow）を定義する。自身では作業（ロジック）を持たない。
    *   **実行モデルの選択**:
        *   **【Role Switching】**: カウンセリングや壁打ちなど、**ユーザーとの直接かつ連続的な対話が必要なタスク**の場合は、サブエージェントを起動してはならない（伝言ゲームになりUXが崩壊するため）。親エージェント自身がフェーズごとにWorkerのSKILLを読み込み、自身の状態（帽子）を切り替えて対話を行う。
        *   **【Subagent Delegation】**: リサーチ、ファイル整理、非同期バッチ処理など、**バックグラウンドで完結するタスク**の場合は、自ら実行するのではなく `invoke_subagent` を用いてタスクを委譲する。
*   **Tier 2: Worker (個別タスクの実行)**
    *   **責務**: 与えられた単一の専門的なタスクを完璧にこなす。

## 2. SOLID原則の適用

1.  **Single Responsibility Principle (単一責任の原則)**
    *   1つのSKILL（特にTier 2）は、1つのタスクだけを行う。
    *   例: 「深掘り対話をしてフォーマットも整える」スキルはNG。「深掘り対話（Interviewer）」と「フォーマット（QA）」に分割する。
2.  **Open-Closed Principle (開放閉鎖の原則)**
    *   既存のスキルを修正せずとも、新しいサブエージェントをオーケストレーターのフローに追加するだけで機能を拡張できるようにする。

## 3. Zettelkastenとの境界線の厳守

*   **Skillは振る舞い、Zettelkastenは知識**。
*   Skillのプロンプト内に「会社の方針」や「特定のプロジェクトの前提知識」をハードコードしてはならない。それらは `10_Areas` や `40_Permanent_Notes` から JIT (Just-In-Time) でロードさせること。

## 4. トレードオフ裁定とアンチパターン

Agentic OSでは「システム（Git等）が事前コミットによって実行時のリスクを担保している」という大前提（GEMINI.md 参照）がある。

*   **【NGパターン】**: エスケープ漏れやインジェクションを恐れて `scratch/` に一時ファイルを作成し、後で `rm` する実装。
    *   **理由**: 途中で異常終了した場合にゴミが残り、Leave No Traceの原則に違反するため。
*   **【推奨パターン】**: ヒアドキュメントやパイプ処理を用いたインメモリでのステートレスな実行。

## 5. ツールの自己浄化 (Garbage Collection)

Agentic OS の保守性と認知負荷の低減を保つため、「どこからも参照されない孤立したファイル」は技術的負債とみなし、検知次第削除すること。

*   **Tools (`tools/`) と Templates (`templates/`)**: いずれかの `SKILL.md` または `docs/` 内で名前が参照されていなければならない。
*   **Jobs (`jobs/`)**: `launchd` の設定ファイル (plist) 等、自動起動設定ファイル内で参照されていなければならない。

この原則は、コミット時のGitフック (`pre-commit`) および `pre_handoff_verify.sh` により物理的に強制・監査される。

## 6. SKILL Naming Convention (ユビキタス言語)

SKILLの名称は、AIがRole（役割）を誤認するノイズを防ぐため、以下の命名規則とユビキタス言語（ボキャブラリー）に厳密に従うこと。

* **フォーマット**: ケバブケース（小文字・ハイフン区切り）
* **構造**: `[ドメイン/手法]-[Role (役割)]` （例: `tdd-red-worker`, `zk-format-reviewer`）

**【Role（接尾辞）のユビキタス言語】**
SKILLの末尾（Role）は必ず以下のいずれかに限定する。`coder`, `writer`, `qa`, `agent`, `builder`, `refactorer` などの非標準ボキャブラリーは使用してはならない。
1. **`-orchestrator`**: (または `-manager`) フローを制御し、他のサブエージェント（ワーカー）を呼び出す司令塔。
2. **`-worker`**: 特定の隔離された実務（テスト作成、実装、調査）のみを実行するステートレスな作業者。（旧 builder / refactorer 統合）
3. **`-reviewer`**: 成果物がルールや基準に合致しているか検閲・監査する者。
4. **`-architect`**: 構造やファイル群の雛形そのものを設計・構築する上位ワーカー。
5. **`-facilitator`**: ユーザーと対話し、思考の整理やメタ認知を促す対話特化役（カウンセラーやインタビュアー等）。
