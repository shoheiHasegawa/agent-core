# SDD & TDD Heuristics (仕様とテストの踏み台)

本ドキュメントは、仕様定義（SDD）、テスト駆動開発（TDD）、およびリファクタリングにおいてAgentがロードすべきヒューリスティクス（思考の踏み台）と、標準的なワークフロー（ダブルループTDD）を定義する。

## 1. ダブルループTDD フロー (Outside-In TDD)
Agentは「メーカー（実装）」と「チェッカー（検証）」の分離体制を基本とし、以下のフローで開発を進めること。

- **Outer Loop (仕様・結合テスト)**
  1. 仕様 (spec.md) を設計し、要求IDとI/O型を明確にする。
  2. 結合テストを作成し、意図的にFAIL（Red）させる（Proof of Red）。バグ修正時も必ず「失敗するテスト」から始めること。
- **Inner Loop (ドメイン実装・単体テスト)**
  3. 必要に応じて単体テストを書きつつドメインを実装し、コードをGreenにする。
  4. SOLID原則に従ってリファクタリングを行い、Greenを維持する。
- **Quality Gate (司法)**
  5. `make check-all` を実行し、静的解析やカバレッジ基準を通過させる。エラーが出た場合はブルートフォースせず原因を言語化すること。

## 2. ベースライン (The Floor / 防護ネット)
* **仕様深掘り**: ユーザーへの質問は本質的な1〜2問に絞ること。
* **4大隠れ異常系**: (1) 暗黙の None/Null (2) 0件・空配列 (3) 境界値 (4) 型不一致
* **リファクタリング3大チェック**: (1) DRY (2) SRP (3) 意図的命名

## 3. メタ認知へのジャンプ (The Trampoline / 問い)
* **仕様定義時**: 「そもそも作らず、既存の仕組みで代用（YAGNI）するとしたら？」
* **テスト作成時**: 「このドメイン特有の『ステータス矛盾』や『事前条件違反』はないか？」
* **リファクタリング時**: 「過剰なDRYにより、将来分離すべきものがCouplingしていないか？」

## 4. ルールの陳腐化条件 (When to break this rule)
* **使い捨てのPoC**: アーキテクチャよりもスピード優先。TDDは省略しフェイルファストで実行する。
* **仕様の自己矛盾**: 無理にテストを通さず、ユーザーに差し戻してバグを共有する。
