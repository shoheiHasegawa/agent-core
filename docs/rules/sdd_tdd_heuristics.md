

# SDD & TDD Heuristics (仕様とテストの踏み台)

本ドキュメントは、仕様定義（SDD）、テスト駆動開発（TDD）、およびリファクタリングにおいてAgentがロードすべきヒューリスティクス（思考の踏み台）を定義する。

## 1. ベースライン (The Floor / 防護ネット)
これらは開発サイクルにおいてAgentが最低限守るべきルール（物理制約）である。

*   **仕様深掘り (Socratic Discovery)**: 
    *   要求定義時は、ユーザーへの質問を最も本質的な1〜2問に絞り、認知負荷を上げないこと。
*   **4大隠れ異常系 (TDD Red)**:
    *   以下の4パターンのテストケースを必ず網羅すること。
        1. 暗黙の None/Null
        2. 0件・空配列
        3. 境界値 (Max+1, Min-1など)
        4. 型不一致
*   **リファクタリング3大チェック (TDD Green)**:
    *   1. DRY (Don't Repeat Yourself)
    *   2. SRP (Single Responsibility Principle)
    *   3. 意図的命名 (Intentional Naming)
*   **エラー・リフレクション (Loop Orchestration)**:
    *   品質ゲート（Linter等）で失敗した際は、ブルートフォース（闇雲な再試行）を禁止し、必ず「なぜ落ちたのか」を言語化してから差し戻すこと。

## 2. メタ認知へのジャンプ (The Trampoline / 問い)
ルールをこなすだけでなく、以下の問い（What if）を自問またはユーザーに投げかけ、局所最適化を防ぐこと。

*   **極端な仮説とYAGNI (仕様定義時)**: 「あえて極端な仮説ですが、もしこの機能をそもそも作らず、既存の仕組みで代用（YAGNI）するとしたらどうなりますか？」
*   **ドメイン特有の異常系 (テスト作成時)**: 「4大異常系はあくまでベースラインです。これらに加えて、このドメイン（業務）特有の『ステータスの矛盾』や『事前条件の違反』はないか？」
*   **過剰な共通化の抑止 (リファクタリング時)**: 「DRYを適用してコードを共通化しましたが、これによって将来、別の理由で変更されるべきものが結合（Coupling）してしまっていないか？」

> [!WARNING]
> ※注意: TDDやリファクタリングなど、Workerスキル (例: `tdd-red-coder`, `tdd-green-refactorer`) によって本ドキュメントがロードされた場合、上記の The Trampoline (推論) は最小化（または無効化）される。Workerは仕様書 (`spec.md`) に基づく即時実行を優先すること。

## 3. ルールの陳腐化条件 (When to break this rule)
以下の条件に当てはまる場合、Agentは上記のルールを疑い、ルールのアップデートや例外適用を提案すること。

*   **使い捨てのスクリプトやPoC (Proof of Concept) の場合**: アーキテクチャの堅牢性（SRPやDRY）や異常系の網羅よりも、スピードが最優先される。この場合、TDDや厳密なリファクタリングのプロセスを省略し、フェイルファストで実行すること。
*   **仕様（`spec.md`）自体に自己矛盾が見つかった場合**: テストを無理にパスさせようとせず、速やかに上流（Socratic Discoveryフェーズ）に差し戻し、仕様自体のバグをユーザーと共有すること。
