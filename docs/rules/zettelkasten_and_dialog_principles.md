# 🧠 Zettelkasten & Socratic Dialog Principles (知識蒸留と対話の原則)

## 🎯 本ドキュメントの存在目的 (WHY)
社長の日常の意思決定やプロジェクトの気づき（ルートBの学び）を `second-brain` へ蓄積する際、**AIが先回りして教科書的で無難な一般論に要約してしまうことで、「社長自身の頭で内省して成長する機会」と「なぜその洞察に至ったかという生々しい熱量（Whyのエントロピー）」が奪われるのを防ぐため**。

---

## 1. WHAT：Zettelkasten ノートの品質基準（守るべき契約）

1. **アトミックノート蒸留境界**:
   - **WHY**: 1つのノートに複数のテーマや一過性の作業手順が混ざると、後から別の文脈と結合（リンク）できなくなるため。
   - **基準**: 1つの Permanent Note には「1つの普遍的な概念や法則」のみを記述する。リポジトリ固有の施工手順やアンチパターンは [`agent-core/docs/experiences/`](../experiences/README.md) へ振り分け、`second-brain` には混ぜない。
2. **「新規作成 vs リライト（差分更新）」の判定境界**:
   - **新規作成（推奨）**: 既存ノートの前提となる上位概念、別角度からの補完・対立概念の場合。独立したアトミックノートとして作成し、双方向リンク（`[[...]]`）でネットワーク化する。
   - **リライト（更新）**: 既存ノートの命題そのものの誤り・修正、または同一定義内のマイナーな補足にとどまる場合。社長へ差分を明示して承認を得て更新する。
3. **「公式キーワード ⇄ 社長のメガネ」バイリンガル原則**:
   - 専門技術や認定資格（CCA-F等）の知見を蒸留する場合、一次情報の正確な英語ターム（例: *Compounding Errors*, *DAG*, *Feedback loop*）と、社長独自の実務アナロジー・世界観を必ず対比・紐付けて記述する（社長独自の知的資産化と試験対策の両立）。
4. **厳格な YAML メタデータ**:
   - `id`: `YYYYMMDDHHMMSS` 形式
   - `tags`: 英語の `snake_case`、階層型（例: `domain/agentic_architecture`）。日本語や CamelCase は禁止。
   - `aliases`: 日本語の短い名詞句（2〜3単語）。
5. **弁証法的な双方向リンク**:
   - 関連ノートへのリンクは `[[...]]` を用い、単なる関連ではなく `[Conflict]`（対立）、`[Support]`（根拠）、`[Narrower]`（具体化）などの関係性を明示する。

---

## 2. 🛡️ GOVERNANCE：知識庫純度を守る絶対制約 (Hard Constraints)

1. **Agent単独での Permanent 化の禁止 (Zettelkasten Philosophy)**:
   - Agentがタスク完了時等に知見を `sense_making/` へ自動投函することは許可するが、`permanent_notes/` への移管・新規登録をAgent単独で完結させることは【絶対に禁止】とする。必ず社長とのソクラテス対話を経て、社長自身の言葉として蒸留した後にのみ登録が許される。
2. **直接ファイル書き込みの禁止 (Architectural Governance)**:
   - Agentが `write_file` やシェルコマンド等で `second-brain` 配下の日常ノートを直接作成・編集することは【絶対に禁止】とする。テンプレート崩れやタグバリデーションすり抜けを防ぐため、必ず `core-service` の公式CLI（`make zk-register`, `zk-update`, `zk-delete`）を唯一の窓口として実行しなければならない。保護領域（`areas/`, `resources/`, `templates/`）の変更は Worktree＋PR が必須である。
3. **未整形データの投函禁止**:
   - 人間の乱雑な手書きメモや未パースのログ等を直接投函してはならない。必ずMarkdownとして整形・洗練された状態でのみ投入する。

---

## 2. HOW：ソクラテス式壁打ちと熱量保存のプロトコル

1. **Collision First（対立・矛盾からの問いかけ）**:
   - いきなりAIがまとめ案を書くのではなく、「一般論（または過去のノート）では〇〇と言われるが、今回の実体験ではなぜ△△という逆の結論になったのか？」という対比・矛盾を1〜2問投げかけ、社長自身の言葉で `WHY` を語らせる。
2. **思考の生鮮保存（AI要約による平滑化の防止 — `[EXP-06]`）**:
   - AI特有の綺麗に整った一般論に丸めてはならない。社長が語った生々しい比喩（例：「裸の王様化」「足し算バイアス」）、トレードオフの葛藤、具体例をそのままノートの核として残す。
3. **WHY ➔ WHAT ➔ HOW による普遍化**:
   - 個別の現象から「①なぜその問題が起きるのか（構造的WHY）➔ ②どうあるべきか（普遍的WHAT）➔ ③どう制御するか（実践的HOW）」の順で構造化し、他のビジネスや組織運営にも応用できる知的資産（IP）へ昇華させる。
4. **緊急時のフェイルファスト例外**:
   - 社長が単なる迅速なメモ記録（Inbox投入）や緊急対応を求めている時は、過度な深掘り対話を行わず即座に実行へ移る。
