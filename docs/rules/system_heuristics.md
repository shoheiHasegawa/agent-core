# System & Architecture Heuristics (OS管理とアーキテクチャの踏み台)

本ドキュメントは、Agentic OSのセッション管理（起動・終了）、ワークスペースの監査、およびアーキテクチャ境界の遵守においてAgentがロードすべきヒューリスティクス（思考の踏み台）を定義する。

## 1. ベースライン (The Floor / 防護ネット)
これらはOSの健全性とSSOT（Single Source of Truth）を保つための物理制約である。

*   **Zero-Queue 状態管理 (Session Manager)**: 
    *   すべてのセッションは `tasks/context.md` (RAM: 高頻度更新) と `tasks/progress.md` (HDD: 低頻度更新) を正本として再開・管理される。
*   **自律的な更新 (Zero-Prompt Update)**:
    *   エージェントはユーザーからの「進捗を更新して」という指示を待たず、自律的に上記2つのドキュメントを更新すること。
*   **論理的アーキテクチャ境界の遵守 (Compliance Reviewer)**:
    *   **インフラ層へのドメイン浸透**: インフラ層がドメイン固有のステータス文字列等を直接知ってはいけない。
    *   **ドメイン層へのインフラ浸透**: ドメイン層が特定のライブラリやフレームワークに依存してはいけない。

## 2. メタ認知へのジャンプ (The Trampoline / 問い)
ルールをこなすだけでなく、以下の問い（What if）を自問またはユーザーに投げかけ、システムのエントロピー増大を防ぐこと。

*   **教訓の抽出 (セッション終了時)**: 「単に進捗を記録して終わるのではなく、今回のセッションの議論や失敗から、将来の意思決定に活かせる教訓やメタ知識（Why）は得られなかったか？」
*   **ルールの陳腐化の疑い (コンプライアンス監査時)**: 「もし実装コードが『ドメイン層へのインフラ浸透』ルールに違反しているとしたら、それはコードが悪いのか？ それとも、現在のビジネス要求に対して『既存のルール（またはアーキテクチャ）自体が合わなくなって陳腐化している』からなのか？」

## 3. ルールの陳腐化条件 (When to break this rule)
以下の条件に当てはまる場合、Agentは上記のルールを疑い、ルールのアップデート（立法府への差し戻し）を提案すること。

*   **アーキテクチャルールの形骸化**: ルールを遵守するためだけに、無駄なデータ詰め替え（マッピング）クラスが大量発生し、逆にシステムの認知負荷が極端に上がっている場合。これは「関心の分離」の手段が目的化しているサインであり、ルールの緩和（またはCQRSなどの別パラダイムへの移行）を提案すべきである。
*   **セッションコンテキストの肥大化**: `tasks/context.md` が50行を超えてもなお情報が溢れる場合。これはEpicのスコープが大きすぎるサインであり、コンテキストを強制的にZettelkastenへ退避させ、Epicの分割をユーザーに提案すること。
