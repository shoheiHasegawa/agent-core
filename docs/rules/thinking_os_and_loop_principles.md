# 🧠 Thinking OS, SDD/TDD & Loop Principles (思考のOS・6大観点・2-Passループ原則)

本ドキュメントは、You_Inc の全 Agent が意思決定・仕様定義・実装・レビューを行う際の「思考プロセス（第一原理）」「SDD 6大観点」「自律ループの制御規約」を統合定義する正本ルールである。

---

## 1. 思考のOS（第一原理）と「引き算ファースト」

### 1.1 引き算ファーストの原則 (Subtraction-First Principle)
AIはエラー対応や指摘修正において、既存の構造を壊すのを恐れて「上に `if` 文を足す」「引数を足す」「ラッパーを足す」「ルールに例外を1行足す」という**足し算（パッチ当て）を選ぶ強いバイアス（Additive Bias）**を持つ。
これを防ぐため、すべての変更において以下の思考順序（アルゴリズム）を強制する：

1. **🗑️ Step 1: Delete（削除できないか？）**
   - 何かを追加する前に、「不要な処理・引数・分岐・責務・ファイルを**消すことで問題を解決できないか？**」を最初に問え。
2. **🔄 Step 2: Simplify / Replace（単純な構造に置換できないか？）**
   - 既存の歪んだ構造の上にパッチを貼るのではなく、「元のクラスや関数の責務自体を**よりシンプルな形に書き換えられないか？**」を問え。
3. **➕ Step 3: Add（最小限の追加 — YAGNI）**
   - Step 1・2 が不可能な場合のみ、現在の契約（`spec.md` の分母）を満たす最小限のコードのみを追加せよ。「将来使うかもしれない拡張性」の先回り実装は固く禁ずる。

### 1.2 DDD & SOLID の思考プロセス
Outside-In TDD で外側のテストを早く通そうとすると、UseCase にすべての条件分岐や計算をベタ書きした「手続き型のファットUseCase（貧血ドメインモデル）」に陥りやすい。以下の問いを常に立てよ：
- **Single Responsibility (SRP)**: このクラスを変更する理由は1つだけか？ UseCase は「手順のオーケストレーション」だけを行い、ビジネスルールや不変条件は `Domain` 層（Entity / ValueObject）が持っているか？
- **Dependency Inversion (DIP)**: `Domain` / `Application` 層が `Infrastructure` 層の具象クラスや外部ライブラリ（SQLAlchemy等）を直接インポートしていないか？

## 2. SDD（仕様駆動開発）の6大観点マトリクス（分母の定義基準）

実装に入る前に `spec.md` でシナリオID（検査の分母）を固定する際は、以下の **6大観点** から抜け漏れなく洗い出せ：

1. **正常系 (Happy Path)**: 標準的な入力に対して期待される主たる出力・状態遷移。
2. **冪等性 (Idempotency)**: 同一の入力やコマンドを複数回実行した際に、重複作成や状態破壊が起きないこと。
3. **境界値 (Boundary Conditions)**: 0件、空文字、空配列、上限・下限値、日付境界における振る舞い。
4. **外部同期・調停 (Reconciliation)**: 外部API・ファイルシステム・DBとの状態不整合が発生した際の洗い替え・整合維持。
5. **異常系・耐障害性 (Fault Tolerance)**: 不正な入力、ファイル不在、外部通信エラー時のFail-Fastな例外送出とロールバック。
6. **ドメイン不変条件 (Domain Invariants)**: エンティティや値オブジェクトがどのような操作を経ても絶対に破ってはならないビジネスルール。

## 3. 後続工程への波及（Downstream Impact）を軸にした重要度判定

レビュー指摘や課題の重要度（`MUST` / `SHOULD` / `IMO`）は、単なる「見た目の大きさ」ではなく、**「放置した時に後続の工程（別コンテキストのAgent）へどれだけ誤解と手戻りを増幅させるか（ブルウィップ効果）」** を軸に判定する。

| レベル | 定義と判定基準（後続波及リスク） | ループ制御上の扱い |
| :--- | :--- | :--- |
| 🔴 **`MUST`**<br>(Blocker) | **1. 上流（`spec.md` やI/O契約）の曖昧さ・記述ミス・シナリオ漏れ**：見た目が1文字の揺れでも、後続の `tdd-red-worker` が誤解して全工程が手戻りするため無条件で `MUST`。<br>**2. 契約未達・テスト失敗・重大なDDD境界違反（逆依存等）**。 | **即座に差し戻し（修正必須）**。<br>`MUST == 0` になるまで次へ進めない。 |
| 🟡 **`SHOULD`**<br>(Pass 2 洗練) | **契約と動作は満たし後続も狂わせないが、構造の美しさ・保守性に改善余地があるもの**（例：UseCaseからDomainへのロジック抽出、重複統合、命名改善）。 | **Pass 1（1周目）では差し戻さずリスト化し、Pass 2（2周目）で一括解消する**。 |
| 🟢 **`IMO`**<br>(Skip / YAGNI) | **今回の分母（`spec.md`）スコープ外の将来構想・別アプローチの提案・好み**。 | **今回のループでは修正禁止（過品質防止）**。必要なら経験ストックやBacklogへメモするのみ。 |

## 4. 自律ループの5大定義項目と「2-Pass スパイラル構造」

「1周で完璧なコードを作ろうとして迷走する」「指摘ゼロを目指して永遠にループが終わらない」問題を防ぐため、開発ループは必ず以下の **2段階（Pass 1 ➔ Pass 2）** で回し、定量的な完了・停止条件を厳守する。

1. **📋 Phase 0（上流ゲート：分母の固定と曖昧さ排除）**:
   - 実装に入る前に `spec.md` の6大観点シナリオID（分母）を固定し、後続が誤解する曖昧さ（🔴 `MUST`）をゼロにする。
2. **🌀 Pass 1（1周目：貫通 — Make it Work）**:
   - 小バッチ（1回につき1〜2シナリオ）で `tdd-red-worker` ➔ `tdd-green-worker` を回し、まずは全シナリオを一通り Green にする（全体を通して動かす）。
   - ここでのレビューは 🔴 `MUST`（契約漏れ・バグ）のみを修正対象とし、1周動かしてみて初めて見えた構造上の課題（🟡 `SHOULD`）はリストに記録して Pass 2 へ送る。
3. **✨ Pass 2（2周目：全体俯瞰と引き算のリファクタリング — Make it Right）**:
   - 全シナリオのテスト（防波堤）が揃って動いている状態でコード全体を俯瞰し、溜まった 🟡 `SHOULD` の解消、重複コードの削除（引き算）、UseCase から Domain モデルへのロジック抽出を一括で行う。
   - Pass 2 の完了時に最終レビュー（`compliance-reviewer`）を行い、新たな 🟢 `IMO` や重箱の隅の指摘は切り捨ててループを閉じる。

### 定量的・決定論的な完了条件と異常停止条件（Circuit Breaker）
- **✅ 完了条件（Exit Criteria — 決定論的AND条件）**:
  1. 対象リポジトリの `make check-all` の終了コードが `0`（テスト全通過、Cov $\ge 90\%$、SDD差分 `0`）。
  2. 独立レビュアー（`compliance-reviewer`）の 🔴 `MUST` 指摘件数が `0件`。
- **🛑 異常停止条件（Circuit Breaker — 定量的OR条件）**:
  1. **同一エラー・同一 `MUST` 指摘での連続失敗 `== 2回`**。
  2. **1バッチ内の実装⇄レビュー往復 `== 3周`**。
  3. **🔴 Tier 3（前例のない仕様矛盾・未決事項）の発生 `>= 1件`**。
  - 上記のいずれかに達した瞬間、推測やブルートフォースでの再試行を即座にやめ、`tasks/context.md` に「①停止理由、②原因仮説、③再開のためのA/B選択肢」を出力してエスカレーションせよ。
