# 🧠 Thinking OS, SDD/TDD & Loop Principles (思考のOS・6大観点・2-Passループ原則)

## 🎯 本ドキュメントの存在目的 (WHY)
AIエージェントが陥りやすい3大構造欠陥——**「①目的（WHY）を飛ばして手段（HOW）に飛びつく」「②問題解決で常に足し算（パッチ当て）を選んで肥大化させる」「③レビュー指摘が無限に続いて過品質になる（またはテストだけ通してDDDが崩壊する）」**——を思考の第一原理（OS）レベルで防ぎ、高い自律性と設計品質を両立させるため。

---

## 0. 思考の最上位アルゴリズム：`WHY ➔ WHAT ➔ HOW` の順序原則

すべての設計、仕様策定、コード変更、ドキュメント整備、および社長への提案において、いきなり `HOW`（どう実装するか・どう作業するか）から入ることを禁ずる。必ず以下の順序で思考を展開せよ：

1. **🎯 Step 1: WHY（目的・解くべき本質的課題・存在理由）**:
   - 「そもそもなぜこれが必要なのか？」「誰のどんな痛み（またはリスク）を解消するためか？」「これをやらないとどうなるか？」を最初に定義する。
   - **ドキュメント作成時の鉄則**: あらゆるドキュメント（設計書・ルール・仕様書）の冒頭には、必ず **「なぜこのドキュメントが存在し、いつ・何のために参照するのか（WHY）」** を明記せよ。WHYのないルールや設計書は形骸化する。
2. **📐 Step 2: WHAT（満たすべき状態・境界・契約・不変条件）**:
   - WHY を達成するために、「何が満たされていれば成功か（DoD / シナリオ分母）」「どこまでがスコープで、どこからがスコープ外か（境界）」を宣言的に定義する。
3. **🛠️ Step 3: HOW（具体的な構造・手順・実装）**:
   - WHY と WHAT が確定した後に初めて、それを最もシンプルに実現する手段（HOW）を選択する。

## 1. 目的ドリブン（Purpose-Driven）と WHY への純化原則

### 1.1 目的ドリブン（Purpose-Driven）と HOW の代替性・純化原則
- **WHY（なぜ必要か）**: 人間やAIはエラー対応やレビュー指摘において、「指摘の解消」という目先のHOWが目的化しやすく、既存構造の上に安易なパッチや例外を上塗りする強い足し算バイアス（Additive Bias）を持つため。そもそもの目的（WHY）を見失うと、コードもルールも無限に肥大化し脱線する。
- **WHAT（目指す状態）**: 「そもそも何のため？（WHY）」という目的に常に立ち返り、目的が強固にロックされていることで、目的に寄与しない不要なパッチが自然に削ぎ落とされ（純化）、必要に応じて他の最適な手段（HOW）へと柔軟に代替できる状態。
- **HOW（現場の実践アルゴリズム — Purpose ➔ Delete ➔ Simplify ➔ Add）**:
  指摘対応や設計変更時には「HOWの目的化」を断ち切るため、以下の順序で思考せよ：
  1. **🎯 Purpose Check（目的に立ち返る）**: 「この変更はそもそも何の目的（WHY）のためか？ 指摘の字面を潰すための安易なパッチになっていないか？ WHYが明確なら、別のより適切なHOWはないか？」を最初に問え。
  2. **🗑️ Delete（目的外の不要物を削除・純化できないか？）**: 何かを足す前に、目的に寄与しない不要な処理・引数・分岐・責務・パッチを**消すことで問題を解決できないか？** を問え。
  3. **🔄 Simplify / Replace（シンプルな構造に置換できないか？）**: 歪んだ構造の上にパッチを貼るのではなく、目的に照らして**よりシンプルな構造に書き換えられないか？** を問え。
  4. **➕ Add（最小限の追加 — YAGNI）**: 上記の純化を経ても目的に対して真に必要な場合のみ、最小限の構造を追加せよ。「将来使うかもしれない拡張性」の先回り実装は固く禁ずる。
  - ⚠️ **過剰な引き算の防止（`[EXP-15]` 準拠）**: 引き算を行う際、アクセスパターンの異なるファイル（短期メモリの `context.md` と長期目標の `AGENTS.md` 等）を単一ファイルに統合してコンテキストを汚染させたり、各ルールから「なぜその制約があるか（1行のWHY）」まで削ぎ落として不変条件（チェスタトンのフェンス）を失わせてはならない。削る対象は「他ファイルとの重複コピペ」と「廃止済みのゾンビ資産」に限定せよ。

### 1.2 DDD & SOLID の思考プロセス
- **WHY（なぜ必要か）**: Outside-In TDD で外側のテストを最短で通そうとすると、UseCase にすべての条件分岐や計算をベタ書きした「手続き型のファットUseCase（貧血ドメインモデル）」に陥り、仕様変更に脆くなるため。
- **WHAT / HOW（常に立てるべき問い）**:
  - **Single Responsibility (SRP)**: このクラスを変更する理由は1つだけか？ UseCase は「手順のオーケストレーション」だけを行い、ビジネスルールや不変条件は `Domain` 層（Entity / ValueObject）へ抽出されているか？
  - **Dependency Inversion (DIP)**: `Domain` / `Application` 層が `Infrastructure` 層の具象クラスや外部ライブラリ（SQLAlchemy等）を直接インポートしていないか？

## 2. SDD（仕様駆動開発）の6大観点マトリクス（分母の定義基準）

- **WHY（なぜ必要か）**: 実装に入る前に「検査の分母（全要求シナリオ）」を固定しないと、テストの抜け漏れが起きるか、逆にレビュー工程で「あれも足りない」と後出しジャンケンが起きてループが収束しなくなるため。
- **WHAT / HOW（6大観点による分母の洗い出し）**: `spec.md` でシナリオIDを定義する際は、以下の6つのレンズで抜け漏れなく洗い出せ：
  1. **正常系 (Happy Path)**: 標準的な入力に対して期待される主たる出力・状態遷移。
  2. **冪等性 (Idempotency)**: 同一の入力やコマンドを複数回実行した際に、重複作成や状態破壊が起きないこと。
  3. **境界値 (Boundary Conditions)**: 0件、空文字、空配列、上限・下限値、日付境界における振る舞い。
  4. **外部同期・調停 (Reconciliation)**: 外部API・ファイルシステム・DBとの状態不整合が発生した際の洗い替え・整合維持。
  5. **異常系・耐障害性 (Fault Tolerance)**: 不正な入力、ファイル不在、外部通信エラー時のFail-Fastな例外送出とロールバック。
  6. **ドメイン不変条件 (Domain Invariants)**: エンティティや値オブジェクトがどのような操作を経ても絶対に破ってはならないビジネスルール。

## 3. 後続工程への波及（Downstream Impact）を軸にした重要度判定

- **WHY（なぜ必要か）**: 「指摘ゼロになるまでループする」と定義すると、レビュアーの無限指摘バイアスにより重箱の隅をつつく過品質ループに陥る。一方で、上流（`spec.md`）の小さな曖昧さを「軽微（IMO）」として見逃すと、後続の別Agentが誤解して全工程が手戻りするため。
- **WHAT / HOW（後続波及リスクに基づく3分類）**:

| レベル | 定義と判定基準（後続へのブルウィップ効果） | ループ制御上の扱い |
| :--- | :--- | :--- |
| 🔴 **`MUST`**<br>(Blocker) | **1. 上流（`spec.md` やI/O契約）の曖昧さ・記述ミス・シナリオ漏れ**：見た目が1文字の揺れでも、後続の `tdd-red-worker` が誤解して全工程が手戻りするため無条件で `MUST`。<br>**2. 契約未達・テスト失敗・重大なDDD境界違反（逆依存等）**。 | **即座に差し戻し（修正必須）**。<br>`MUST == 0` になるまで次へ進めない。 |
| 🟡 **`SHOULD`**<br>(Pass 2 洗練) | **契約と動作は満たし後続も狂わせないが、1周動かした結果見えた構造改善**（例：UseCaseからDomainへのロジック抽出、重複統合、DTOへの不要な足し算パッチの除去）。 | **Pass 1（1周目）では差し戻さずリスト化し、Pass 2（2周目）で一括解消する**。 |
| 🟢 **`IMO`**<br>(Skip / YAGNI) | **今回の分母（`spec.md`）スコープ外の将来構想・別アプローチの提案・好み**。 | **今回のループでは修正禁止（過品質防止）**。必要なら経験ストックやBacklogへメモするのみ。 |

## 4. 自律ループの5大定義項目と「2-Pass スパイラル構造」

- **WHY（なぜ2周に分けるのか）**: 1周目から完璧な抽象化やリファクタリングを求めると、全体が動く前に設計迷子になる。まず1周目で全シナリオを貫通させて「100%のテスト防波堤」を作ってから、2周目で全体を俯瞰して「引き算のリファクタリング」を行う方が、手戻りが最小かつ設計純度が最も高くなるため。
- **HOW（2-Pass スパイラルと定量的停止条件）**:
  1. **📋 Phase 0（上流ゲート：分母の固定と曖昧さ排除）**: `spec.md` の6大観点シナリオID（分母）を固定し、後続が誤解する曖昧さ（🔴 `MUST`）をゼロにする。
  2. **🌀 Pass 1（1周目：貫通 — Make it Work）**: 小バッチ（1〜2シナリオずつ）で `tdd-red-worker` ➔ `tdd-green-worker` を回し、全シナリオを一通り Green にする（🔴 `MUST` のみ解消、🟡 `SHOULD` は記録して保留）。
  3. **✨ Pass 2（2周目：全体俯瞰と引き算 — Make it Right）**: 全テストが通った状態で全体を俯瞰し、溜まった 🟡 `SHOULD` の解消、不要コードの引き算、UseCase から Domain へのロジック抽出を一括で行い、`compliance-reviewer` の最終確認で閉じる。

### 定量的・決定論的な完了条件と異常停止条件（Circuit Breaker）
- **✅ 完了条件（Exit Criteria — 決定論的AND条件）**:
  1. 対象リポジトリの `make check-all` の終了コードが `0`（テスト全通過、Cov $\ge 90\%$、SDD差分 `0`）。
  2. 独立レビュアー（`compliance-reviewer`）の 🔴 `MUST` 指摘件数が `0件`。
- **🛑 異常停止条件（Circuit Breaker — 定量的OR条件）**:
  1. **同一エラー・同一 `MUST` 指摘での連続失敗 `== 2回`**。
  2. **1バッチ内の実装⇄レビュー往復 `== 3周`**。
  3. **🔴 Tier 3（前例のない仕様矛盾・未決事項）の発生 `>= 1件`**。
  - 上記のいずれかに達した瞬間、推測での再試行を即座にやめ、`tasks/context.md` に「①停止理由、②原因仮説、③再開のためのA/B選択肢」を出力してエスカレーションせよ。
