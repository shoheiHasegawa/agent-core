# Zettelkasten Heuristics (第二の脳の踏み台)

本ドキュメントは、Zettelkasten（第二の脳）へのノート蒸留およびフォーマット整形においてAgentがロードすべきヒューリスティクス（思考の踏み台）を定義する。

## 1. ベースライン (The Floor / 防護ネット)
これらはZettelkastenの健全性を保つために最低限守るべきルール（物理制約）である。

*   **アトミックノート蒸留境界**: 
    *   1つのノートには「1つの普遍的な概念や法則」のみを記述すること。単なる「今日のタスクの記録」や「一過性のバグ修正ログ」はPermanent Noteとして保存してはならない。
*   **厳格なYAMLメタデータ**:
    *   `id`: YYYYMMDDHHMMSS形式
    *   `tags`: 英語のsnake_case、階層型（例: `#domain/machine_learning`）に強制変換。日本語やCamelCaseは禁止。
    *   `aliases`: 日本語の短い名詞句（2〜3単語）。
*   **弁証法的な双方向リンク**:
    *   関連ノートへのリンクは `[[...]]` を用いること。
    *   単なる「関連」ではなく、`[Conflict]`（対立）、`[Support]`（根拠）、`[Narrower]`（具体化）などの関係性を付与すること。

## 2. メタ認知へのジャンプ (The Trampoline / 問い)
ルールをこなすだけでなく、以下の問い（What if）を自問し、情報のエントロピー（無秩序化）を防ぐこと。

*   **抽象度の強制引き上げ**: 「このノートのタイトルや内容は、特定のツール名や固有のプロジェクト名に依存しすぎていないか？ それを別のドメインでも通用する普遍的な法則に書き換えるとしたら、どう表現できるか？」
*   **思考の生鮮保存（平滑化の防止）**: 「AIとして綺麗な文章に整えすぎていないか？ ユーザーの生々しい表現や『棘（とげ）』、感情の乗ったコンテキストの熱量を殺してしまっていないか？」
*   **既存ノートとの衝突・統合**: 「この新規ノートは、既存のノートAと実質的に同じことを言っていないか？ であれば、新規作成ではなく既存ノートのアップデート（追記）に留めるべきではないか？」

## 3. ルールの陳腐化条件 (When to break this rule)
以下の条件に当てはまる場合、Agentは上記のルールを疑い、ルールのアップデートを提案すること。

*   **ドメインの専門用語がsnake_caseにそぐわない時**: どうしてもCamelCaseや特定の記号が必要な分野（例: C#の命名規則に関するノートなど）において、無理にルールを適用して意味が通じなくなる場合は、フォーマットルールの例外適用を提案すること。
*   **リンクのネットワークが密になりすぎた時**: すべてのノートが相互にリンクされすぎ、中心的なノート（ハブ）が肥大化している場合は、リンクの付与を一時停止し、インデックスノート（MOC）の作成に切り替えること。
